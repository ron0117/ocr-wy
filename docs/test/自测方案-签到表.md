# 自测方案 · 签到表

依据 [需求梳理版](../detail/需求-签到表-梳理版.md)、[技术设计](../design/技术设计-签到表.md) 和 [开发计划](../plan/开发计划-签到表.md)。本文只规定怎么测，不改代码。

本地自测核对接口的路由、入参和结果。页面是否好用由使用人自行看，不作为通过条件。企业微信里真正点开卡片，放在域名和 IP 白名单就绪之后。

## 测试范围

| 纳入 | 不纳入 |
|---|---|
| 发布活动的校验、多俱乐部、同一企业微信团队 | 按「是否绑定通知」筛选 |
| 发送失败时活动仍发布，并留下通知记录 | 活动二维码、个人微信扫码签到 |
| 绑定唯一、签到每场一次、发布后不看开始时间 | 玩家自己换绑 |
| 人员列表返回是否绑定，解除绑定，删除人员时去掉绑定 | 企业微信团队的创建和切换页面 |
| 签到情况含未签到的人，且只含本场俱乐部 | 通讯录全量同步、企业微信打卡 |
| 提醒只发给已绑定且属于本场俱乐部的人 | Redis、BullMQ、跨活动签到总表 |
| 结束活动后不能再签、不能再发 | 全站性能和并发压测 |
| 管理员与玩家令牌互不通用 | 界面点击流程 |

## 环境与前置

| 项 | 要求 |
|---|---|
| 数据库 | PostgreSQL 已迁移，存在 `wecom_teams`、`activities`、`activity_clubs`、`activity_recipients`、`wecom_bindings`、`activity_check_ins`、`activity_notifications`，且 `clubs.wecomTeamId` 已加上 |
| API | NestJS 已启动，请求前缀 `/api/v1` |
| 账号 | 两个管理员账号，记为甲、乙。各自至少有一个俱乐部和一名人员 |
| 企业微信未配置 | 去掉 `WECOM_CORP_ID`、`WECOM_AGENT_ID`、`WECOM_SECRET`、`WEB_ORIGIN` 之一后重启 API，只用于 CFG 用例 |
| 企业微信已配置 | 四项都有值。本地发得出去与否都可以，用例看活动行和通知记录，不看手机是否弹出卡片 |
| 玩家令牌 | 由 OAuth 回调签发后再测 PL 用例。没有令牌时，PL 用例记为未测 |
| 第二团队 | 只有 AC-04 需要。在测试库另插一个 `wecom_teams`，并把甲名下另一个俱乐部的 `wecomTeamId` 改到该团队。测完改回 |

下面用「活动请求」表示 `POST /activities` 的一份合法正文：甲自己的至少一个俱乐部、非空标题、开始时间、提醒时间为空或晚于当前时间，以及至少一项部门、标签或成员 ID。

## 用例

### 配置与俱乐部

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| CFG-01 | 技术设计 | 企业微信未配置时，用活动请求调用 `POST /activities` | 返回未配置。`activities` 不新增行 |
| CFG-02 | 回归 | 同一状态下调用 `GET /clubs`、`GET /members`，并新增一名人员 | 与签到功能加入前一致，不因缺少企业微信配置失败 |
| CFG-03 | 一团队 | 配好企业微信并重启后，再新建一个俱乐部 | 该俱乐部的 `wecomTeamId` 等于唯一团队。已有空值俱乐部也被填上 |
| CB-01 | 技术设计 | 某俱乐部已被一场活动选中时，`DELETE /clubs/:id` | 返回 409。俱乐部、活动和人员都还在 |

### 发布与归属

企业微信已配置后执行。

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| AC-01 | 验收 1、Q1 | 分别提交空标题、空 `clubIds`、接收范围三项都空、提醒时间不晚于当前时间 | 每次都是 400。都不创建活动 |
| AC-02 | UC-01、UC-02 | 用甲的两个俱乐部和一份非空接收范围发布 | 活动状态为 `PUBLISHED`。`activity_clubs` 有两行。有一条 `PUBLISH` 通知。企业微信拒收时通知为 `FAILED`，活动仍是已发布 |
| AC-03 | 验收 10 | 活动请求里的俱乐部改成乙的俱乐部 | 返回 404。不创建活动 |
| AC-04 | 验收 1 | 活动请求同时带上甲的原团队俱乐部和第二团队俱乐部 | 返回 400。不创建活动 |
| AC-05 | 验收 10 | 乙调用 `GET /activities`，并 `GET /activities/:id` 使用甲的活动 id | 列表没有甲的活动。详情返回 404 |
| AC-06 | Q2 | 对甲的活动调用两次 `POST /activities/:id/end` | 第一次后状态为 `ENDED` 且有 `endedAt`。第二次仍是已结束，不新开一场 |
| AC-07 | UC-09、Q2 | 已结束的活动调用 `POST /activities/:id/notifications`，`kind` 分别为 `publish` 和 `remind` | 两次都是 409。不新增通知 |

### 人员列表与绑定列

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| MB-01 | UC-06、验收 8 | `GET /members`，并新增加一名人员后再查 | 每行有 `notifyBound`。新人员为 `false` |
| MB-02 | UC-06 | `GET /members?sort=notifyBound&order=asc`，再换 `desc` | 升序时未绑定在前。降序时已绑定在前。原有排序字段仍然可用 |
| MB-03 | 验收 8 | `POST /members` 或 `PATCH /members/:id` 的正文带上 `notifyBound` | 返回 400。该人员的绑定状态不变 |
| MB-04 | 验收 8 | 用俱乐部和玩家名称关键字筛选，并按排名排序 | 与原来的人员列表一致 |
| MB-05 | UC-08 | 对未绑定人员调用 `DELETE /members/:id/wecom-binding` | 返回已是未绑定。人员还在 |
| MB-06 | Q3 | 该人员已绑定后再次 `GET /members`，然后解除绑定 | 绑定后该行为 `true`。解除后为 `false`。人员其他列不变。若已有签到，签到时间仍在 |
| MB-07 | Q4 | 删除已绑定人员，再用同一个企业微信 userid 绑定本场另一个未占用角色 | 原人员消失。新绑定成功。原角色不再占用该 userid |
| MB-08 | 梳理版绑定 | 已绑定人员被编辑或被同名导入覆盖后再查绑定 | `wecom_bindings` 仍指向原来的 `members.id` |

### 玩家身份、绑定与签到

没有玩家令牌时，本组记为未测，不改记为通过。

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| PL-01 | 技术设计 | 用玩家令牌调用 `GET /members` 和 `POST /activities` | 被拒绝。不返回人员，也不创建活动 |
| PL-02 | UC-04、验收 3 | 未绑定成员打开已发布活动 `GET /player/activities/:id` | `phase` 为 `unbound`。`candidates` 只有本场已选俱乐部里未占用的角色，且带俱乐部名称 |
| PL-03 | 验收 3、4 | `POST /player/activities/:id/binding`，选一个候选角色 | 成功。`GET /members` 中该行 `notifyBound` 为 `true` |
| PL-04 | 验收 4 | 同一令牌再绑另一个角色；另一个企业微信成员再绑 PL-03 的角色 | 两次都是 409。库里仍是原来的那一对 |
| PL-05 | UC-05、验收 5、7 | 开始时间设在当前时间之后，调用 `POST /player/activities/:id/check-in` | 成功并返回 `checkedAt`。开始时间未到也可以签 |
| PL-06 | 验收 5 | 立刻再调用一次签到 | 不新增签到行。`checkedAt` 与第一次相同 |
| PL-07 | 验收 6 | 令牌已绑定的角色不属于这场已选俱乐部时，再请求活动和签到，并尝试绑定本场角色 | `phase` 为 `other_club`。签到和绑定都是 409 |
| PL-08 | Q2 | 活动结束后再 `GET /player/activities/:id`，并调用绑定和签到 | `phase` 为 `closed`。已有 `checkedAt` 仍返回。绑定和签到都是 409 |

### 签到情况

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| CK-01 | UC-07、Q5 | 甲调用 `GET /activities/:id/check-ins` | 行里含玩家名称、所属俱乐部、`notifyBound`、`checkedIn`、`checkedAt`。两个已选俱乐部的当前人员都在 |
| CK-02 | UC-07 | 查看未绑定人员，以及未选中俱乐部里的人员 | 未绑定人员 `checkedIn` 为 false，`checkedAt` 为空。未选中俱乐部的人员不在结果里 |

### 提醒与再次发送

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| RM-01 | Q1、验收 9 | 发布时 `remindAt` 为空，等待超过一分钟后看通知表 | 没有 `trigger` 为 `AUTO` 且 `kind` 为 `REMIND` 的记录 |
| RM-02 | UC-03、验收 9 | 发布时 `remindAt` 设为约一分钟后。本场只有一部分角色已绑定，且其中一名绑定角色属于别的俱乐部 | 到点后只有一条自动提醒。接收人只包括已绑定且角色属于本场俱乐部的 userid。没有这样的人时，该条为 `SENT`，接收人数为 0 |
| RM-03 | 技术设计 | RM-02 之后再等一分钟 | 不再新增第二条自动提醒 |
| RM-04 | UC-09 | 对仍是已发布的活动调用 `POST /activities/:id/notifications`，`kind` 为 `publish`，再以 `remind` 调用一次 | 各新增一条通知。`publish` 仍用当初的部门、标签或成员。`remind` 按当时已绑定且属于本场的人重新计算 |

### 真机收发

可信域名、应用可见范围和 IP 白名单就绪后执行。未执行则记为未测。

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| WX-01 | UC-02、验收 2 | 发布时选一个在应用可见范围内的成员。该成员在企业微信里点开卡片 | 进入 `/a/:id`，能识别为该成员，并出现 PL-02 的选角色或签到 |
| WX-02 | 非功能 | 用个人微信或普通浏览器打开同一个活动链接 | 不能绑定，也不能签到 |
| WX-03 | 验收 9 | 等到 RM-02 的提醒时间 | 已绑定且属于本场俱乐部的成员收到提醒卡片。未绑定的成员收不到这张提醒 |
| WX-04 | UC-09 | 接收范围里放一个不在可见范围内、会被企业微信拒绝的对象后发布 | 活动仍是已发布。对应通知为失败，并且能看到失败说明 |

## 通过与失败

本地自测同时满足下面各项才算通过：

1. CFG-01、CFG-02、CFG-03、CB-01 的期望都出现。
2. AC-01 至 AC-07、MB-01 至 MB-08、CK-01、CK-02、RM-01 至 RM-04 的期望都出现。
3. 已取得玩家令牌时，PL-01 至 PL-08 的期望都出现。
4. AC-01、AC-03、AC-04、CFG-01 之后，活动行数与操作前一致。

任一已执行的 Must 用例失败，即整版不通过。

玩家令牌还没有时，PL 用例保持未测，本地自测不算通过。真机用例 WX-01 至 WX-04 未执行时，签到表整版不算通过；这不推翻已经通过的本地接口结果，域名就绪后只补这四条。

## 回归要点

| 项 | 期望 |
|---|---|
| 登录 | 未带管理员令牌时，`/clubs`、`/members`、`/activities` 被拒绝 |
| 人员原功能 | 筛选、排序、新增、编辑、删除仍可用。新列不在新增和编辑的合法字段里 |
| 导入 | 按俱乐部和玩家名称覆盖同一人时，绑定还在 |
| 俱乐部删除 | 没有人员和活动引用时，仍可删除 |
| 页面 | 菜单、活动页和窄屏由使用人自行看，不作为本方案的通过条件 |
