# 自测方案 · 签到表 2.0

依据 [需求梳理版](../detail/需求-签到表2.0-梳理版.md)、[技术设计](../design/技术设计-签到表2.0.md) 和 [开发计划](../plan/开发计划-签到表2.0.md)。本文只规定怎么测，不改代码。

自测以 **接口最小请求** 核对路由、入参、出参与错误文案为主。页面布局、二维码扫码、iframe 嵌入是否美观由使用人自行看，**不作为通过条件**。小忧、企微 1.0 玩家链路不在范围内。

## 测试范围

| 纳入 | 不纳入 |
|---|---|
| 活动发布字段与归属（现网规则） | 企微卡片、OAuth、`/player/*` |
| 公开 `GET/POST public/activities/:id` | 浏览器点击流、E2E |
| 报名写入 `activity_registrations` | 压测、严格并发 IP 第 6 条 |
| IP 5 次/活动、唯一 `(活动,俱乐部,名称)` | 小忧问答 |
| 活动查看 CRUD、全量活动下拉、排序筛选 | 新报名进入活跃度弹窗 |
| 卸 `activities/:id/attendance` | 自动化测试套件 |
| 导入不再 NEED_RENAME / 不认领 attendance | 界面导出文件肉眼版式（可选 spot check） |
| 菜单 permission 注入 `activity-registrations` | |
| `ENDED` 不可 POST 报名 | |

## 环境与前置

| 项 | 要求 |
|---|---|
| 数据库 | PostgreSQL 已迁移，存在 `activity_registrations` 及枚举；`activity_attendances` 可保留历史行 |
| API | NestJS 已启动，前缀 `/api/v1`；若走反向代理，与 `trust proxy` 配置一致 |
| 账号 | 管理员甲、乙各一；甲至少两个俱乐部 A1、A2，乙有俱乐部 B1；甲在 A1 下至少一名人员（供导入用例） |
| JWT | 甲、乙各取 `Authorization: Bearer …`（登录接口） |
| 公开请求 | **不带** JWT；可用 curl，必要时加 `X-Forwarded-For: 203.0.113.1` 等固定 IP 测限流 |
| 活动正文 | 「活动请求」= `POST /activities` 合法 body：`title`、`clubIds`（甲可见）、`startsAt`、可选 `note` |

记 `ACT` = 甲发布成功后返回的活动 id；`CLUB` = 该活动关联的某一俱乐部 id。

## 用例

### 活动发布与链接（UC-01、验收 1、13）

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| AC-01 | 验收 1 | 提交空标题、空 `clubIds`、非法 `startsAt` | 400，不创建活动 |
| AC-02 | UC-01 | 甲用 A1、A2 发布 | 201/`PUBLISHED`；`activity_clubs` 两行；**无**企微通知调用（无新 notification 亦可） |
| AC-03 | 验收 10 | 活动请求带乙的 B1 | 404 或 403（与现网一致），不创建 |
| AC-04 | UC-01 | `GET /activities/:id`（甲 token） | 含 `title`、`clubIds`/clubs；若有 `publicUrl` 则形如 `{WEB_ORIGIN}/a/{ACT}` |
| AC-05 | 验收 13 | 无 token 访问 Web 路由 `/a/{ACT}`（实现后可选）或仅验 API 公开 GET | 公开 GET 活动摘要可 200（见 PU-01） |

### 公开读活动（UC-02）

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| PU-01 | UC-02 | `GET /public/activities/{ACT}` 无 JWT | 200；`status`=`PUBLISHED`；`clubs` 仅 A1、A2，含 id、name |
| PU-02 | — | `GET /public/activities/{随机 uuid}` | 404 |
| PU-03 | C4 | 对 ACT 调用 `POST /activities/{ACT}/end` 后，再 `GET /public/activities/{ACT}` | 200；`status`=`ENDED` |

### 公开提交报名（UC-02、UC-03、验收 3–6、11–12）

合法 body 示例：

```json
{
  "clubId": "<CLUB>",
  "playerName": "测试非凡者",
  "score": 12345,
  "profession": "WARRIOR"
}
```

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| RG-01 | UC-02、验收 6 | `POST /public/activities/{ACT}/registrations`（ACT 为 PUBLISHED） | 201；库中 `activity_registrations` 新增一行；`attendanceStatus`=NORMAL；`members` 无变化；`activity_attendances` **无**新行 |
| RG-02 | 验收 5 | `score`: 0、-1、9999999、1.5 | 400，不入库 |
| RG-03 | 验收 3 | 与 RG-01 相同 `playerName`+`clubId` 再 POST 一次 | 409/400，文案含「当前活动已报名」；仍只有 1 行 |
| RG-04 | 验收 3 | 同 `playerName`，换 ACT 下**另一**已选俱乐部 | 201（若俱乐部不同则允许） |
| RG-05 | C4 | ACT 已 ENDED 后 POST 同上 body | 400，文案含结束/无法报名；不入库 |
| RG-06 | 验收 4 | 固定 `X-Forwarded-For: 203.0.113.10`，对同一 ACT 用 **不同** `playerName`+合法 body 成功 POST **5 次** | 前 5 次 201 |
| RG-07 | 验收 4 | 第 6 次仍换名 POST | 400，文案「您已报名多次，报名失败」 |
| RG-08 | 技术设计 | RG-03 重复失败后再 POST 新名（同 IP） | 若已成功 5 次则仍 RG-07；重复失败 **不计入** 5 次（总成功仍 ≤5 时可 201） |
| RG-09 | — | `clubId` 用未关联 ACT 的俱乐部 | 400，不入库 |
| RG-10 | — | 无 JWT 调用 `POST /activities` | 401 |

### 卸旧签到接口（UC-08）

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| OLD-01 | UC-08 | `GET /activities/{ACT}/attendance`、`PUT` 同路径（甲 token） | **404** 或路由不存在；不可再勾选保存 |

### 活动查看 API（UC-04、UC-05、验收 8、10、11）

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| AR-01 | 验收 10 | 乙 token 调用 `GET /activity-registrations/activities` | 200；列表含甲发布的 ACT（**不按**乙俱乐部过滤） |
| AR-02 | UC-04 | `GET /activity-registrations?activityId={ACT}` | 200；`rows` 含 RG-01 记录；字段含 clubName、score、profession、attendanceStatus、createdAt |
| AR-03 | UC-04 | 同上 + `clubId={A1}` | 仅 A1 报名；`clubId={A2}` 过滤正确 |
| AR-04 | UC-04 | `sortBy=playerName&sortOrder=asc` | 顺序与库一致（服务端排序） |
| AR-05 | UC-05、验收 11 | `PATCH /activity-registrations/{id}`，`attendanceStatus`: `LATE` | 200；再 PATCH 为 `ABSENT`；再为 `NORMAL`；库中互斥单值 |
| AR-06 | UC-05 | PATCH 改 `playerName` 为已存在的同活动同俱乐部名 | 409/400 唯一冲突 |
| AR-07 | UC-05 | `DELETE /activity-registrations/{id}` | 204/200；再 GET 列表无该行 |
| AR-08 | — | 无 token 调用 AR-01 | 401 |

### 权限与菜单（验收 10）

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| PM-01 | 验收 10 | 乙 token `POST /permission`（或登录后 menus 接口） | 返回菜单含「活动查看」/`activity-registrations`，**即使**角色未勾选该键 |
| PM-02 | — | 乙 token 调 AR-02 | 200（活动查看 API 不依赖 `activities` menuKey） |

### 导入与 members（UC-09、验收 9）

前置：A1 下人员 P1 曾在旧逻辑下有一条 `activity_attendances`（可选，有则测只读）；新报名仅在新表。

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| IM-01 | UC-09 | 导入确认后，本次名单不含 P1 | P1 被删或按现网「未出现则删除」；**不**返回 `NEED_RENAME` 409 |
| IM-02 | UC-09 | 导入新建与 P1 同名人员 | **不**自动更新 `activity_attendances.memberId`；新表报名不受影响 |
| IM-03 | 验收 9 | `PATCH /members/{id}` 改 playerName | `activity_attendances` 上快照**不**随改名更新（若仍有历史行） |
| IM-04 | 梳理版 | 新表有报名后，导入任意操作 | `activity_registrations` 行数与内容不变 |

### 活跃度只读旧表（回归）

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| HA-01 | 梳理版 | 甲对仅有 **新表报名**、无 attendance 的人员调 `GET /members/{id}/activities` | `attended` **不**含该 ACT（新报名不出现） |
| HA-02 | — | 若库中仍有带 `memberId` 的旧 attendance | `attended` 仍可见对应活动（只读遗留） |

### 导出（UC-07）

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| EX-01 | UC-07 | 前端导出或若后续有导出 API，用 AR-02 同条件拉全量 | 行数与列表一致；**接口自测**以 AR-02 全量为准；文件版式使用人可选打开 xlsx  spot check |

## 通过与失败

**通过（本地自测）** 须同时满足：

1. AC-01～AC-04、PU-01～PU-03、RG-01～RG-10、OLD-01 期望均成立。
2. AR-01～AR-08、PM-01～PM-02 期望均成立。
3. IM-01～IM-04、HA-01 期望均成立（HA-02 有历史数据则测）。
4. 任一 Must 用例失败即 **不通过**，记录接口路径、状态码与响应体。

**未测不计通过**：Web 路由 `/a/:id` 仅 UI 时记未测，但 PU/RG 公开 API 必须通过。

## 回归要点

- `POST /activities`、`PATCH/DELETE/END` 仍遵守甲/乙俱乐部可见性。
- `GET /members`、手工增删改人员仍可用。
- 小忧活动相关接口行为与改前一致（不查新表）。
