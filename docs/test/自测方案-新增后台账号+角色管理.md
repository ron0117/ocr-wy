# 自测方案 · 新增后台账号+角色管理

依据 [需求梳理版](../detail/需求-新增后台账号+角色管理-梳理版.md)、[技术设计](../design/技术设计-新增后台账号+角色管理.md) 和 [开发计划](../plan/开发计划-新增后台账号+角色管理.md)。本文只规定怎么测，不改代码。

本地自测核对接口的路由、入参和结果。侧栏、账号页和角色页是否好用由使用人自行看，不作为通过条件。

## 测试范围

| 纳入 | 不纳入 |
|---|---|
| 超级管理员登录，以及 `POST /permission` 只返回菜单 | 一个账号多个角色 |
| 账号增删改查、停用与再次启用、修改密码 | 菜单目录本身的增删改 |
| 角色绑定菜单和俱乐部，以及越权修改超级管理员 | 忘记密码、邮件重置密码 |
| 新建俱乐部自动进入创建者角色 | 玩家签到改走后台账号 |
| 人员、导入、活动只出现在已绑定俱乐部内 | 把任务、模板改成按角色过滤 |
| 已有账号在迁移后停用；重启不再把已启用账号停掉 | 全站性能和并发压测 |
| 注册接口关闭 | 界面点击流程 |

## 环境与前置

| 项 | 要求 |
|---|---|
| 数据库 | PostgreSQL 已迁移。存在 `roles`、`role_menus`、`role_clubs`，`users` 有 `roleId` 和 `disabled` |
| API | NestJS 已启动，请求前缀 `/api/v1` |
| 超级管理员 | `SUPER_ADMIN_EMAIL`、`SUPER_ADMIN_PASSWORD` 已配置。下文称为超管 |
| 俱乐部 | 至少两个已有俱乐部，记为 A、B。可以由超管先创建 |
| 旧账号 | 迁移前已经存在的邮箱，记为旧号。空库没有旧号时，OLD-01 记为未测，不因此判失败 |
| 玩家令牌 | 只用于 PL-01。没有企业微信令牌时，PL-01 记为未测 |

下文「甲」是测试中创建的普通账号，角色只含俱乐部 A，菜单只含 `clubs`、`members`、`activities`。「乙」是另一个普通账号，角色只含俱乐部 B，菜单只含 `members`。两个角色都不要勾 `accounts` 和 `roles`，除非某条用例明确要求。

令牌放在 `Authorization: Bearer`。`POST /permission` 不带请求体。

## 用例

### 预置与迁移

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| OLD-01 | UC-09、验收 2 | 用旧号和它原来的密码调用 `POST /auth/login` | 401，文案为「邮箱或密码不正确」。不返回令牌 |
| CFG-01 | UC-01、验收 1、Q1 | 用超管调用 `POST /auth/login`，再 `POST /permission`，再 `GET /clubs` | 登录成功。菜单含俱乐部管理和系统管理下的全部子菜单，且带 `key`、`title`、`path`。俱乐部列表含 A 和 B。响应里没有俱乐部 id 列表这种权限字段 |
| CFG-02 | 技术设计 | 超管账号已经存在时，改掉环境变量里的密码并重启 API，再用原密码登录 | 仍能用原密码登录。重启不覆盖已有密码 |
| CFG-03 | 验收 2、风险 | 把甲启用后重启 API，再用甲登录 | 甲仍然可以登录。重启不把非超管重新停用 |

### 登录与菜单

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| AU-01 | 验收 10 | 调用 `POST /auth/register`，正文含邮箱和至少 8 位密码 | 路由不存在。不新增用户 |
| AU-02 | UC-04、验收 5 | 超管把甲停用后，用甲登录 | 401，文案为「邮箱或密码不正确」 |
| AU-03 | 验收 5、Q7 | 甲先登录拿到令牌，超管再把甲停用，甲用原令牌调用 `GET /clubs` | 401 |
| AU-04 | UC-02、验收 3 | 不带令牌、以及带非法令牌，分别调用 `POST /permission` | 两次都是 401 |
| AU-05 | Q8 | 创建一个菜单键为空的角色和账号，登录后调用 `POST /permission` | 登录成功。响应为 `{ "menus": [] }`，状态 200 |
| AU-06 | Q7、验收 3 | 甲保持原令牌。超管把它的角色改成只含 `members`。甲再调用 `POST /permission` 和 `GET /clubs` | 菜单只剩人员列表。俱乐部仍只受该角色的俱乐部绑定限制。不需要重新登录才生效 |
| PL-01 | 验收 10 | 用玩家令牌调用 `POST /permission` 和 `GET /accounts` | 被拒绝。不返回后台菜单，也不返回账号列表 |

没有玩家令牌时，PL-01 记为未测。

### 账号

用超管的令牌，除非某条写明用别人。

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| AC-01 | 验收 4 | 分别缺少邮箱、密码、`roleId`，以及密码短于 8 位，调用 `POST /accounts` | 每次都是 400。都不创建用户 |
| AC-02 | UC-03、验收 4 | 创建甲：合法邮箱、至少 8 位密码、一个普通角色 | 成功。`disabled` 为 false。列表能看到邮箱、名称、角色，看不到密码哈希 |
| AC-03 | 验收 4 | 用甲的邮箱再创建一次 | 409。用户仍是一行 |
| AC-04 | Q2 | `roleId` 传超级管理员角色，调用 `POST /accounts` | 409。没有新的超级管理员 |
| AC-05 | UC-10、验收 5 | `PATCH /accounts/:id` 不带密码，只改名称；再用原密码登录。然后带上新密码再改一次 | 第一次原密码仍可登录。第二次只有新密码可登录 |
| AC-06 | UC-04、验收 5 | 停用甲后再启用，用甲登录并调用 `POST /permission` | 停用期间不能登录。启用后可以登录，菜单和俱乐部与它的角色一致 |
| AC-07 | Q6、验收 9 | 超管对自己调用删除，再调用停用 | 两次都是 409。超管仍可登录 |
| AC-08 | 验收 9、Q2 | 删除超管账号；把超管的 `roleId` 改成普通角色；把超管设为停用 | 三次都是 409。超管的角色和启用状态不变 |
| AC-09 | 验收 2 | 旧号 `roleId` 为空时，只把 `disabled` 改成 false，不带 `roleId` | 400。该账号仍然不能登录 |
| AC-10 | UC-03 | 给 AC-09 的账号同时带上普通角色并启用，再登录 | 可以登录。菜单和俱乐部等于这个角色 |
| AC-11 | 技术设计 | 删除甲。再 `GET /clubs` 查看甲创建过的俱乐部 | 甲不能再登录。俱乐部还在，超管仍能看到 |
| AC-12 | UC-10 | `GET /accounts?email=` 使用甲邮箱的一段 | 只返回邮箱包含这段的账号 |
| AC-13 | UC-08 | 用没有 `accounts` 菜单的甲调用 `POST /accounts`、`PATCH /accounts/:id`、`DELETE /accounts/:id` | 三次都是 403 |

### 角色

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| RL-01 | UC-05 | 创建一个角色，勾选 `clubs` 和 `members`，并绑定俱乐部 A | 成功。列表里的菜单数量为 2，俱乐部数量为 1，并带回菜单键和俱乐部 id |
| RL-02 | Q4 | 用 RL-01 的名称再创建一次 | 409 |
| RL-03 | 技术设计 | `menuKeys` 传入 `not-a-menu` 或父级键 `club-management` | 400。角色菜单绑定不变 |
| RL-04 | Q5、验收 9 | 角色下仍有甲时 `DELETE /roles/:id` | 409。甲的 `roleId` 不变 |
| RL-05 | Q5 | 把甲改到另一个角色后，再删除 RL-04 的角色 | 删除成功。该角色的菜单绑定和俱乐部绑定一并消失 |
| RL-06 | Q2、验收 9 | 对超级管理员角色调用 `PATCH /roles/:id` 和 `DELETE /roles/:id` | 两次都是 409。超管的菜单和可见俱乐部不变 |
| RL-07 | Q3 | 超管先给某角色绑上俱乐部 B。再让一个只能看到俱乐部 A、且持有 `roles` 的账号保存该角色，正文里的 `clubIds` 只有 A | 保存成功。该角色仍然绑着 B，同时也绑着 A |
| RL-08 | Q3 | 同一个普通账号把 `clubIds` 设成只有 B | 400。绑定不被改成只有 B |
| RL-09 | 技术设计 | 只持有 `accounts`、没有 `roles` 的账号调用 `GET /roles`，再调用 `POST /roles` | 列表成功，且不含超级管理员角色。创建为 403 |
| RL-10 | UC-08 | 甲没有 `accounts` 也没有 `roles` 时调用 `GET /roles` | 403 |

### 俱乐部、人员与活动

先让甲只能看到 A，乙只能看到 B。

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| SC-01 | UC-06、验收 6 | 甲调用 `GET /clubs`，再按 B 的 id 修改或删除 | 列表只有 A。对 B 的修改和删除都是 404，B 不变 |
| SC-02 | UC-07、验收 7、8 | 甲新建俱乐部 C。甲、乙、超管分别 `GET /clubs` | 甲的列表出现 C。乙的列表没有 C。超管的列表有 C |
| SC-03 | 技术设计 | 超管新建俱乐部 D。甲再 `GET /clubs` | 超管能看到 D。甲的列表没有 D，直到把 D 绑到甲的角色 |
| SC-04 | 技术设计 | 甲、乙各自建一个同名俱乐部。超管 `GET /clubs` | 两行都在。两行都能看出各自的创建人邮箱 |
| SC-05 | UC-06、验收 6 | 甲 `GET /members`，再向 B 导入或在 B 下新增人员 | 人员结果只含 A。对 B 的导入和新增为 404，B 的人员不变 |
| SC-06 | 验收 6 | 用 A 和 B 一起发布一场活动。甲、乙分别 `GET /activities/:id` 和签到情况 | 甲和乙都是 404。超管可以打开 |
| SC-07 | UC-06 | 把 B 也绑到甲的角色后，甲再打开 SC-06 这场活动 | 甲可以看到。活动的创建人不是甲也可以 |
| SC-08 | 技术设计 | 甲只绑着 A 时，`POST /activities` 的 `clubIds` 同时包含 A 和 B | 404。不创建活动 |
| SC-09 | 技术设计 | 甲发布一场只含 A 的活动后，从甲的角色解绑 A，甲再 `GET /activities/:id` | 404。超管仍能看到这场活动 |

## 通过与失败

本地自测同时满足下面各项才算通过：

1. CFG-01、CFG-02、CFG-03、AU-01 至 AU-06 的期望都出现。
2. AC-01 至 AC-13、RL-01 至 RL-10、SC-01 至 SC-09 的期望都出现。
3. 库里存在旧号时，OLD-01 的期望出现。
4. 已有玩家令牌时，PL-01 的期望出现。
5. AC-01、AC-03、AC-04、AU-01、SC-08 之后，对应用户、角色或活动的行数与操作前一致。

任一已执行的 Must 用例失败，即整版不通过。

空库没有旧号时，OLD-01 保持未测，不阻止其余用例通过。没有玩家令牌时，PL-01 保持未测，不阻止其余用例通过。

## 回归要点

| 项 | 期望 |
|---|---|
| 未登录 | 不带管理端令牌时，`/clubs`、`/members`、`/activities`、`/accounts`、`/roles` 被拒绝 |
| 玩家页 | 企业微信活动页仍不要求后台角色。签到主路径不在本方案重测 |
| 任务与模板 | 若这些旧接口仍在，仍只返回当前创建人的数据，不按角色绑定放宽 |
| 俱乐部删除 | 删除俱乐部后，`role_clubs` 里对应行消失。没有人员、导入和活动引用时，原删除规则仍可用 |
| 人员原功能 | 在可见俱乐部内，筛选、排序、新增、编辑、删除、导入仍可用 |
| 页面 | 侧栏、账号页、角色页和窄屏由使用人自行看，不作为本方案的通过条件 |
