# 自测方案 · 活跃度

依据 [需求梳理版](../detail/需求-活跃度-梳理版.md)、[技术设计](../design/技术设计-活跃度.md) 和 [开发计划](../plan/开发计划-活跃度.md)。本文只规定怎么测，不改代码。

本地自测核对接口的路由、入参和结果。菜单挂在哪、绿字和红字好不好看，由使用人自行看，不作为通过条件。

## 测试范围

| 纳入 | 不纳入 |
|---|---|
| 发布只收标题、俱乐部、开始时间；可改、可删、可结束 | 旧 `activity_check_ins` 迁移成新勾选 |
| 签到与迟到的保存、重复保存、结束后仍可改 | 小忧发布、修改或代为勾选 |
| 活跃度查询的已签到、未签到、迟到 | 小忧按时间范围筛选 |
| 导入对照 409、对照后 id 不变、未对照后同名认领 | 自动把两个不同名称并成一个人 |
| 去掉通知、玩家签到、企微接口和绑定列 | 删除企微表或活动表上不用的列 |
| 小忧只读回答活动，且不再回答绑定 | 签到打分、导出参加名单、界面点击流程 |

## 环境与前置

| 项 | 要求 |
|---|---|
| 数据库 | 已迁移。存在 `activity_attendances`，含 `late`。`activities.wecomTeamId` 可空。`activity_check_ins` 等企微表仍在 |
| API | NestJS 已启动，请求前缀 `/api/v1` |
| 账号 | 管理员甲、乙。甲至少有两个可见俱乐部，每个俱乐部至少两名人员。乙有另一个俱乐部，看不见甲的俱乐部 |
| 活动请求 | `POST /activities` 的合法正文只有非空 `title`、甲的至少一个 `clubIds`、`startsAt`。不带提醒、部门、标签、成员 |
| 小忧 | `POST /assistant/sessions` 取会话，再 `POST /assistant/sessions/:id/messages`。正文含 `text` 和 `clientRequestId` |

下面把甲的两名人员记为张三、李四，俱乐部记为甲俱乐部。

## 用例

### 菜单与发布

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| MN-01 | UC-01、验收 1 | 甲调用 `POST /permission` | `menus` 里有分组「活动管理」，其下有 `activities` / 「活动签到」。俱乐部管理的子项里没有活动签到。没有「人员参与情况」 |
| AC-01 | 验收 2 | 分别提交空标题、空 `clubIds`、非法时间 | 每次 400。不新增活动 |
| AC-02 | UC-02、验收 2 | 用甲的两个俱乐部发布。正文不带提醒和接收人，企微可以未配置 | 201 或 200。状态 `PUBLISHED`。两个俱乐部都写入 `activity_clubs`。`wecomTeamId`、`remindAt` 为空。没有新的通知行 |
| AC-03 | 验收 2 | 活动请求里的俱乐部改成乙的俱乐部 | 404。不创建活动 |
| AC-04 | 验收 12 | 发布过程中查看通知表，并调用已卸下的 `POST /activities/:id/notifications`、`GET /wecom/audience` | 通知表没有这次发布的新行。两个旧接口 404 |
| AC-05 | UC-03、验收 3 | `PATCH /activities/:id` 改标题、只留一个俱乐部、改开始时间 | 三项都变。已有参加记录还在 |
| AC-06 | 验收 3 | 乙 `GET /activities`，并对甲的活动调用详情、修改、删除 | 列表没有甲的活动。其余都是 404 |
| AC-07 | UC-03 | 甲 `DELETE /activities/:id` | 活动和该活动的 `activity_attendances` 都没有了 |
| AC-08 | Q7、验收 6 | 对已发布活动调用两次 `POST /activities/:id/end`，然后在结束后 `PATCH` 和 `PUT /attendance` | 第一次后为 `ENDED` 且有 `endedAt`。第二次仍是已结束。修改和签到都成功 |

### 签到与迟到

先发布一场只含甲俱乐部的活动。张三、李四都在册。

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| CK-01 | UC-04、验收 4 | `GET /activities/:id/attendance` | 只有甲俱乐部当前人员。每行有 `id`、`playerName`、`clubName`、`attended`、`late`。初始 `attended` 和 `late` 都为假 |
| CK-02 | UC-04、验收 4、7 | `PUT /attendance`，`marks` 为张三 `{ late: false }`、李四 `{ late: true }`。再 PUT 一次相同内容 | 张三一条记录且 `late` 为假。李四一条记录且 `late` 为真。第二次不增加行 |
| CK-03 | 验收 4 | 再 PUT，只保留张三且 `late` 为假 | 李四的记录删除。张三仍在且不迟到 |
| CK-04 | 验收 4 | PUT 只提交李四 `{ late: true }`，不把李四放进「仅签到」的另一份列表 | 李四有一条记录，`attended` 为真，`late` 为真 |
| CK-05 | Q5 | 先给张三签到。再 `PATCH` 活动，俱乐部改成甲的另一个俱乐部，且张三不在其中。再 `GET /attendance` | 弹窗结果里没有张三。张三原来的参加记录仍在库里 |
| CK-06 | 验收 6 | AC-08 的已结束活动上重复 CK-02 | 保存成功。结束状态不变 |

### 活跃度

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| HS-01 | UC-06、验收 8 | 李四已迟到签到、张三未签到时，分别 `GET /members/:id/activities` | 李四的 `attended` 含这场且 `late` 为真，`missed` 不含这场。张三相反，且没有 `late` |
| HS-02 | Q6、验收 8 | 另发布一场，俱乐部只有甲的另一个俱乐部，两人都没签 | 两个人的 `attended` 和 `missed` 都不含这场 |
| HS-03 | 验收 5 | 查看 HS-01 的字段 | 接口给出已签到或未签到所依赖的归属，以及 `late`。不返回「未迟到」这个状态。绿字和红字由使用人在页面上确认 |
| HS-04 | 验收 8 | `GET /members` | 行上没有 `notifyBound`。`DELETE /members/:id/wecom-binding` 为 404。筛选、排序、新增、编辑、删除仍可用 |

### 导入、改名与认领

张三已有一场迟到记录。导入用 `POST /clubs/:clubId/imports`，`files` 加 `rows`。

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| IM-01 | 验收 9 | `rows` 仍含张三，且张三有迟到记录。确认导入 | 张三的人员 id 不变。活跃度里这场仍在，`late` 仍为真 |
| IM-02 | Q1、验收 10 | `rows` 去掉张三，并新增名称「张三丰」。不带 `renames` | 409，体为 `NEED_RENAME`。`missing` 含张三的 id、名称和场数，`arriving` 含「张三丰」。人员表和参加记录与导入前一致 |
| IM-03 | 验收 10 | 用同一批文件和行再提交，`renames` 把张三的 id 对到「张三丰」 | 成功。人员 id 仍是张三原来的 id，名称变为张三丰。不另建一行。参加记录的名称快照变为张三丰，`late` 仍为真 |
| IM-04 | 验收 10 | 再次制造 IM-02 的缺失，`renames` 传空数组 | 成功。原人员行删除。参加记录还在，`memberId` 为空，名称仍是旧名，`late` 仍为真。新名称另建新行，其活跃度里还没有这场 |
| IM-05 | 验收 9、10 | IM-04 之后，再导入同一个旧名称 | 新行的 id 与被删行不同。空挂记录的 `memberId` 变为这个新 id。`GET /members/:id/activities` 能看到原来那场，且 `late` 仍为真 |
| IM-06 | Q1 | `renames` 里同一个新名称对两个旧 id，或旧 id 不在 `missing` 里 | 400。人员表不变 |
| IM-07 | 验收 10 | 在人员列表把李四改名，再查活跃度和参加记录 | 人员 id 不变。参加记录名称快照变为新名。`late` 不变 |
| IM-08 | 方案 B | 删除一名已签到人员，再查 `activity_attendances` | 人员行没有了。对应记录还在，`memberId` 为空，`late` 保留 |

### 小忧

甲需同时有 `activities` 和 `members` 菜单。每问一句使用新的 `clientRequestId`。

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| XY-01 | UC-08、验收 11 | 发送「有哪些活动」 | 回复能看出甲可见活动的标题。不含乙的活动。不创建、不修改活动 |
| XY-02 | UC-08、验收 11 | 发送某一场的标题，问什么时候、谁参加了 | 回复含开始时间、已签到和未签到的人数。迟到的人能被说成迟到 |
| XY-03 | 验收 11 | 发送「张三参加了哪些活动」 | 回复与 HS-01 一致：已签到、未签到、迟到的场次对得上。不说「未迟到」 |
| XY-04 | UC-07、验收 11 | 发送「张三的绑定状态」或「企业微信绑定了吗」 | 回复不出现「已绑定」或「未绑定」。说明不再提供绑定状态 |
| XY-05 | UC-08 | 发送「帮我发布一场活动」或「给张三签到」 | 不新增活动，也不新增参加记录 |
| XY-06 | 技术设计 | 用只有 `members`、没有 `activities` 的账号问「有哪些活动」；用只有 `activities` 的账号问「张三参加了哪些」 | 前者不能列出活动。后者不能按人查询活跃度 |

单边名单超过 30 人时再补一条：回复先说人数，点名不超过 30 人，并说明还有多少人。人数不到 30 时不测这条。

## 通过与失败

本地自测同时满足下面各项才算通过：

1. MN-01、AC-01 至 AC-08 的期望都出现。
2. CK-01 至 CK-06、HS-01 至 HS-04 的期望都出现。
3. IM-01 至 IM-08 的期望都出现。
4. XY-01 至 XY-06 的期望都出现。
5. AC-01、AC-03、IM-02、IM-06 之后，活动和人员的行数与操作前一致。

任一已执行用例失败，即整版不通过。小忧模型暂时不可用时，XY 用例改走本地规则；本地规则也答不对，则整版不通过。

## 回归要点

| 项 | 期望 |
|---|---|
| 登录 | 未带管理员令牌时，`/activities`、`/members`、`/assistant/sessions` 被拒绝 |
| 人员原功能 | 筛选、排序、新增、编辑、删除、导出仍可用。导出列里没有绑定 |
| 同名导入 | 名称不变时人员 id 不变，已有迟到还在 |
| 俱乐部删除 | 被活动使用时仍不能删除 |
| 旧签到 | `activity_check_ins` 的旧行还在，新的签到请求不写这张表 |
| 页面 | 「活动管理」的位置、两列勾选、已签到绿字、未签到和迟到红字由使用人自行看，不作为本方案的通过条件 |
