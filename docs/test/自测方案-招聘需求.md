# 自测方案 · 招聘需求

依据 [需求梳理版](../detail/需求-招聘需求-梳理版.md)、[技术设计](../design/技术设计-招聘需求.md) 和 [开发计划](../plan/开发计划-招聘需求.md)。本文只规定怎么测，不改代码。

## 测试范围

| 纳入 | 不纳入 |
|---|---|
| 不登录打开 `/apply`，五项必填，成功和失败反馈 | 验证码、限流、申请人查询进度 |
| `GET /apply/clubs`、`POST /apply` 不校验登录 | 分页、按工会或处理状态筛选、导出、删除申请 |
| 招聘管理菜单、未读 / 已读、详情、同意 / 不同意 | 同意后写入人员列表 |
| 无菜单不能访问申请列表和对应接口 | 修改俱乐部原有的删除条件 |
| 非超级管理员只看自己角色范围内的俱乐部申请 | 全站性能和并发压测 |

界面自测覆盖未登录申请页、超级管理员的申请列表，以及一个没有「申请列表」菜单的账号。桌面宽度看完整表格；约 390px 只确认申请页的五项和提交按钮仍可操作。

## 环境与前置

| 项 | 要求 |
|---|---|
| 数据库 | PostgreSQL 已迁移，存在 `applications` |
| API | NestJS 已启动 |
| Web | Vite 已启动 |
| 超级管理员 | 能登录，记为甲。甲能看到「招聘管理 / 申请列表」 |
| 受限账号 | 记为乙。角色没有 `applications` 菜单，只分配俱乐部 B |
| 俱乐部 | 至少两个：俱乐部 A、俱乐部 B。A 没有人员、也没有被活动引用，以便最后删除 |
| 人员对照 | 测同意 / 不同意前，记下甲可见的人员行数 |

下面用「合法申请」表示一份正文：游戏名称「测试玩家」、非凡评分 `100`、uid「uid-1」、`clubId` 为俱乐部 A、理由「想来」。

## 用例

### 公开申请

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| AP-01 | UC-01、UC-02、验收 1 | 未登录打开 `/apply` | 看到「无忧大家庭欢迎你的加入~」。没有管理侧栏，没有小忧面板 |
| AP-02 | UC-04、验收 2 | 不带令牌请求 `GET /api/v1/apply/clubs`；再带一个任意 `Authorization` 重试 | 两次都是 200。每项只有 `id` 和 `name`，包含 A 和 B。没有会长、人员 |
| AP-03 | UC-03、验收 3 | 在页面上留空一项后提交；再请求 `POST /api/v1/apply`，正文缺 `reason` | 页面提示失败，已填内容还在。接口 400，不产生申请 |
| AP-04 | Q10 | 游戏名称或 uid 只填空格；理由超过 500 字；评分填负数或小数 | 提交失败，不产生申请 |
| AP-05 | UC-03、UC-05、Q3、Q12、Q13、验收 4 | 连续提交两份合法申请，uid 都是「uid-1」 | 两次都成功。页面清空并提示成功。列表里出现两行，都是未读、待处理 |
| AP-06 | 验收 5 | 记下 A 的 id 后删除 A，再用该 id 提交 | 400，文案为「所选工会不存在」。申请行数不增加 |
| AP-07 | 技术设计 | 浏览器留着过期或任意令牌时提交合法申请 | 接口不是 401，页面不跳到登录页 |

### 管理端

| ID | 对应 | 步骤 | 期望 |
|---|---|---|---|
| AD-01 | UC-06、验收 6 | 甲登录 | 侧栏有「招聘管理」，其下只有「申请列表」 |
| AD-02 | UC-06、验收 6 | 乙登录后看侧栏，并直接打开 `/applications`；再用乙的令牌请求 `GET /api/v1/applications?read=unread` | 乙看不到招聘管理。页面回到乙的可用菜单。接口 403，文案「没有权限」 |
| AD-03 | UC-07、Q8 | 甲打开申请列表 | 默认是未读，能看到 AP-05 的两行。表格有游戏名称、非凡评分、uid、工会名称、提交时间、已读、处理状态。没有理由 |
| AD-04 | Q5、Q6、UC-09、验收 7 | 甲对其中一行点「同意」，不点详情；再点另一行的详情，关闭后再点一次详情 | 只点同意的那行仍是未读，处理状态为同意。详情那行变为已读，未读中消失，已读中出现。第二次打开详情后，已读时间不变 |
| AD-05 | UC-08、Q7、验收 8 | 在详情里把该行改为不同意，再改回同意。每次前后请求 `GET /api/v1/members` | 状态按操作变化，不能改回待处理。人员行数和字段与标记前一致 |
| AD-06 | Q9 | 用一个只有俱乐部 B、且拥有申请列表菜单的账号查看列表 | 看不到俱乐部 A 的申请。直接请求 A 的申请 id 得到 404，文案「申请不存在」 |
| AD-07 | 技术设计 | 甲删除俱乐部 A 之前，先确认 A 没有人员、没有被活动引用。删除后再用甲查看该申请 | 俱乐部删除成功。申请仍在，工会名称仍是删除前的名称 |
| AD-08 | 技术设计 | 不带 `read` 请求申请列表；`PATCH` 正文使用 `PENDING` | 两次都是 400。目标申请的已读和处理状态不变 |

## 通过与失败

同时满足下面各项才算这版自测通过：

1. AP-01 至 AP-07、AD-01 至 AD-08 的期望都出现。
2. AP-03、AP-04、AP-06 之后，申请表没有新增对应的失败行。
3. AD-05 前后人员列表一致。
4. AD-02 的乙不能读到任何申请正文。

任一 Must 用例失败即整版不通过。没有俱乐部 B 或没有受限账号时，AD-02、AD-06 记为未测，整版不算通过。

## 回归要点

| 项 | 期望 |
|---|---|
| 原俱乐部列表 | `GET /api/v1/clubs` 仍要登录。乙只能看到角色范围内的俱乐部 |
| 删除俱乐部 | 有人员或被活动引用时仍不能删除。没有申请不作为删除条件 |
| 人员列表 | 菜单、筛选和原有行不受申请提交、已读、同意、不同意影响 |
| 登录跳转 | 未登录打开 `/applications` 仍到登录页。公开申请接口不触发这条跳转 |
| 外观 | 申请页使用与后台相同的浅蓝色 Element Plus。申请列表是 `el-table` |
