# 开发计划 · 活跃度

依据 [需求梳理版](../detail/需求-活跃度-梳理版.md) 和 [技术设计](../design/技术设计-活跃度.md)。身份用方案 D，未对照的人按方案 B 认领。签到之外另有迟到。本计划只拆任务，不改代码。

## 里程碑

一人按顺序做，大约 6 个工作日。

| 里程碑 | 完成标准 | 建议工期 |
|---|---|---|
| M1 参加记录可写 | 新表已迁移；`wecomTeamId` 可空；删人员不删参加记录；旧签到表不动 | 0.5 天 |
| M2 活动可维护 | 只填标题、俱乐部、时间即可发布；可改、可删、可结束；结束后仍可改签到和迟到 | 1.5 天 |
| M3 导入不丢历史 | 同名更新保留迟到；需要对照时返回 409 且不写库；对照后 id 不变；未对照删除后，同名再出现能认领 | 1.5 天 |
| M4 后台页面 | 「活动管理」下只有活动签到；签到弹窗两列勾选；已签到为绿字，未签到和迟到为红字；绑定列和企微操作消失 | 1.5 天 |
| M5 小忧只读 | 四个活动工具能答已签到、未签到、迟到；绑定问法不再报绑定状态 | 1 天 |

M2 结束可以用接口完成发布和勾选。M3 结束身份规则固定。M4 结束管理员能从页面走完。M5 不阻塞 M4。

## 任务拆分

### M1 数据

- [ ] **P1** 新建 `activity_attendances`：活动、可空人员、俱乐部、名称快照、`late` 默认假、创建时间。活动删除时级联删除。人员删除时 `memberId` 置空。同一活动的非空人员 id 唯一；同一活动、同一俱乐部、同一玩家名称唯一。
- [ ] **P2** `activities.wecomTeamId` 改为可空，列和企微各表保留。不把 `activity_check_ins` 抄进新表。

### M2 活动接口

- [ ] **P3** `POST /api/v1/activities` 只收 `title`、`clubIds`、`startsAt`。至少一个可见俱乐部，可多选。`remindAt` 和接收人留空，`wecomTeamId` 写空。不调用企业微信，不要求企微已配置。
- [ ] **P4** `PATCH /api/v1/activities/:id` 可改标题、俱乐部、开始时间。已结束也能改。更换俱乐部不删除已有参加记录。
- [ ] **P5** `DELETE /api/v1/activities/:id` 删除活动。参加记录随活动级联删除。不可见活动返回 404。
- [ ] **P6** `POST /api/v1/activities/:id/end` 仍只改状态和 `endedAt`。已结束不拒绝之后的修改、删除和签到。
- [ ] **P7** `GET /api/v1/activities/:id/attendance` 返回当前所选俱乐部的在册人员，含 `attended`、`late`。已结束同样返回。不在当前俱乐部里的旧记录不出现。
- [ ] **P8** `PUT /api/v1/activities/:id/attendance`，入参 `marks: [{ memberId, late }]`。人员必须属于当前俱乐部。有标记则插入或更新 `late`；当前名单里没提交的人删除其记录。只提交迟到、没算进签到时，按已签到且迟到写入。不在当前名单里的旧记录保留。同一活动、同一人员只有一条。
- [ ] **P9** 卸下 `POST /activities/:id/notifications`、`GET /activities/:id/check-ins`、玩家活动接口、`/wecom`、提醒定时任务。`ActivitiesModule` 不再引用企微模块。没有其他定时任务时去掉 `ScheduleModule`。列表和详情不再返回通知状态。

### M3 人员身份与活跃度

- [ ] **P10** 确认导入前算出「有历史的缺失」和「待新建名称」。两边都有、且请求没带 `renames` 时返回 409 `{ code: "NEED_RENAME", missing, arriving }`，回滚已上传图片，不改人员。
- [ ] **P11** 带 `renames` 时在原事务里处理：对照项只改旧行名称和字段，人员 id 不变，并改该人参加记录的名称快照，迟到保留；该名称不再新建。一对一，目标必须是本次待新建名称。空数组表示全部不对照。
- [ ] **P12** 未对照的待删除人员照常删除。参加记录留下，`memberId` 为空，名称快照和 `late` 保留。没有历史的缺失人员直接删除，不进对照。没有待新建名称时不返回 409。
- [ ] **P13** 新建人员（导入或手工新增）后，按俱乐部 + 玩家名称认领 `memberId` 为空的记录，并保留 `late`。同一活动已有指向新人员的记录时，留下那条，删掉重复的空挂行。
- [ ] **P14** 人员列表改名时同步该 `memberId` 下的名称快照，不换 id，不改 `late`。
- [ ] **P15** `GET /api/v1/members/:id/activities`。`attended` 是可见且 `memberId` 指向该人的活动，带 `late`。`missed` 是可见、俱乐部包含该人所在俱乐部、且没有该人记录的活动。其他俱乐部的活动不出现。已结束照样出现。

### M4 页面

- [ ] **P16** `MENU_CATALOG` 增加「活动管理」，子项仍是 `activities` / 「活动签到」/ `/activities`，从「俱乐部管理」移出。不新增菜单键。空分组不显示。
- [ ] **P17** 活动列表去掉通知列、重发、签到情况入口。操作保留签到、编辑、删除、结束。发布和编辑弹窗只有标题、俱乐部、开始时间。路由去掉 `/activities/:id` 和 `/a/:id`。
- [ ] **P18** 签到弹窗两列勾选。勾迟到时同时勾上签到；取消签到时同时取消迟到；只取消迟到则签到仍在。已结束可打开并保存。
- [ ] **P19** 人员列表去掉「是否绑定通知」、解除绑定和 `notifyBound` 排序。导出表去掉绑定列。操作列增加「查询活跃度」。
- [ ] **P20** 活跃度弹窗分已签到、未签到。「已签到」用绿字，「未签到」和「迟到」用红字。没勾迟到不显示「迟到」。标题、俱乐部、时间不着色。
- [ ] **P21** 导入核对页收到 `NEED_RENAME` 时打开对照。每行可选一个新名称或不选。确认后用原图片、原行和 `renames` 重新提交。

### M5 小忧

- [ ] **P22** 去掉意图和人员回答里的 `binding`，导出表和帮助文案不再提绑定。问绑定或企业微信时走帮助，说明不再提供绑定状态。全部资料不含绑定。
- [ ] **P23** 增加 `list_activities`、`get_activity`、`activity_roster`、`member_activities`。活动问法先于人员资料匹配。标题匹配沿用全称、确认、选择。前三个要求 `activities` 菜单，第四个要求 `members` 菜单。
- [ ] **P24** 单场回答含已签到、未签到、迟到人数。出席名单里迟到的人标明迟到。某人的活跃度与 P15 同一套规则，并报三类场数。单边超过 30 人时只列前 30 人并说明剩余人数。不能发布、修改、删除、结束或代为勾选。

## 依赖顺序

```text
P1 → P2
P2 → P3 → P4 → P5
P1 → P6
P1 + P4 → P7 → P8
P3 → P9
P1 → P10 → P11 → P12 → P13 → P14
P8 + P13 → P15
P16 可与 P3 并行
P7 + P8 + P16 → P17 → P18
P15 → P19 → P20
P10 → P21
P22 可与 P17 并行
P15 → P23 → P24
```

P16 只改菜单目录，不依赖参加记录。P22 只删绑定文案，不依赖活动查询。P21 要等 409 的字段定下来。P24 要等活跃度查询的已签到、未签到、迟到口径定下来。

## 人力与并行

一个人时按 M1 → M2 → M3 → M4 → M5。P9 放在发布接口改完之后，避免页面还在调用已经卸下的企微接口。

两个人时可以分开：

| 人 | 任务 | 汇合点 |
|---|---|---|
| 甲 | P1–P9，然后 P16–P18 | P8 的 `marks` 定下后，乙才能做活跃度查询 |
| 乙 | P10–P15、P19–P21；P15 定下后做 P22–P24 | P10 的 409 体定下后做导入对照弹窗 |

## MVP 范围

本版做完梳理版里的 Must，以及技术设计已经写明的卸下企微路径。

| 纳入本版 | 对应 |
|---|---|
| 活动签到改挂到「活动管理」 | UC-01、验收 1 |
| 只填标题、俱乐部、时间并发布 | UC-02、验收 2 |
| 修改、删除、结束不锁后续签到 | UC-03、验收 3、6 |
| 签到和迟到两列勾选，可反复保存 | UC-04、UC-05、验收 4、5、7 |
| 活跃度详情：已签到绿字，未签到和迟到红字 | UC-06、验收 5、8 |
| 去掉绑定列、解除绑定、小忧绑定回答 | UC-07、验收 8、11 |
| 小忧四个只读活动工具，含迟到 | UC-08、验收 11 |
| 方案 D 对照；未对照按方案 B 认领 | 验收 9、10 |
| 去掉重发、通知列和玩家自助签到 | UC-09、验收 12 |

不纳入本版：

- 单独的「人员参与情况」菜单
- 把旧 `activity_check_ins` 迁进新表
- 删除活动表上暂不使用的字段和企微表
- 小忧发布、修改或代为勾选
- 小忧按时间范围筛活动
- 签到统计打分、导出参加名单
- 导入时自动把两个不同名称并成同一个人

## 风险与缓冲

| 风险 | 出现在 | 缓冲 |
|---|---|---|
| 对照请求失败后图片已上传 | P10 | 返回 409 时删掉刚上传的对象，核对页留着原文件再提交 |
| 管理员漏对照，改名被当成新人 | P11、P12 | 不自动合并。记录留在旧名称上，只有同名再出现才认领 |
| 认领时同一活动已有一条新人员记录 | P13 | 保留已挂上的那条，删掉空挂重复行，避免撞唯一约束 |
| 更换活动俱乐部后，旧勾选无法在弹窗里取消 | P4、P8 | 这些记录保留，活跃度仍算已签到。弹窗只改当前名单 |
| 页面先上、企微接口后卸，会出现调用 404 | P9、P17 | P17 与 P9 同一批交付，活动页不再请求 audience、通知和玩家接口 |
| 小忧把「谁参加了活动」收成查人员资料 | P23 | 活动问法写在人员资料匹配之前，并用固定说法核对 |

M4 可以在 M5 未完成时先给管理员使用。小忧活动问答不作为活动页面的完成条件。
