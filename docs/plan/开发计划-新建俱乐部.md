# 开发计划 · 新建俱乐部

依据 [需求梳理版](../detail/需求-新建俱乐部-梳理版.md) 和 [技术设计](../design/技术设计-新建俱乐部.md)。本计划只排期和拆任务，不改代码。

升降按技术设计的数据模型处理：库里只存 `previousRank`、`previousScore`，查询时再算出 `rankChange`、`scoreChange`。

## 里程碑

一人按顺序做，大约 5 个工作日。OCR 对样例图的列对齐单独留 1 天缓冲，不挤进功能开发。

| 里程碑 | 完成标准 | 建议工期 |
|---|---|---|
| M1 俱乐部可管理 | 登录用户能增删改查自己的俱乐部；空名称、重名、有人员时删除的规则已生效 | 1 天 |
| M2 表格整理可单测 | 用固定的 OCR 行样例能整理出人员行；0 行、杂讯行、缺名称或排名的行有确定结果 | 1 天 |
| M3 导入可入库 | 上传图片后写入人员；失败不改旧数据；再次导入同一玩家会留下上次排名和评分 | 1.5 天 |
| M4 列表与后台切换 | 三个新页面可用；任务和模板的页面、菜单、接口入口都已去掉 | 1.5 天 |

M1 结束就可以演示俱乐部管理。M3 结束才算导入这条主路径通了。M4 结束才满足「后台不再有任务和模板」。

## 任务拆分

### M1 俱乐部

- [ ] **P1** Prisma 增加 `clubs`、`members`、`import_batches`。`clubs` 以 `(userId, name)` 唯一，`members` 以 `(clubId, playerName)` 唯一。只新增表，不删除旧的任务相关表。
- [ ] **P2** `GET/POST/PATCH/DELETE /api/v1/clubs`。名称空白返回 400，同一用户重名返回 409，会长可空。查询、修改、删除都只触及当前用户的俱乐部，别人的 id 返回 404。
- [ ] **P3** 删除前先数该俱乐部的人员。人数大于 0 返回 409，不级联删除。

### M2 表格整理

- [ ] **P4** 纯函数：输入 OCR `lines`，输出人员行。按纵坐标聚类、按横坐标排序；用「玩家名称」表头划定等级、途径、非凡评分、风尚度、周活跃、入会时间。排名取玩家名称左侧的整数。
- [ ] **P5** 行过滤：没有玩家名称或排名的行丢弃；「主页」「成员列表」「离开俱乐部」这类界面文字丢弃。职位、分组、当前状态不进入结果。
- [ ] **P6** 为 P4、P5 写单元测试。至少覆盖：正常多行、排名在名称左侧、缺表头、有效行数为 0、同一行缺评分仍保留。测试不调用 PaddleOCR。

### M3 导入

- [ ] **P7** `POST /api/v1/clubs/:id/imports`，字段 `file`。校验俱乐部归属、PNG/JPEG/WebP、10MB。未找到俱乐部返回 404。
- [ ] **P8** 调用现有 OCR client。超时或服务不可用返回 502，此时不写人员、不记批次。
- [ ] **P9** 整理结果为 0 行，或找不到「玩家名称」表头，返回 422，不写人员、不记批次。
- [ ] **P10** 有效行大于 0 时，在一个事务里按「俱乐部 + 玩家名称」插入或覆盖。新玩家的上次排名和评分为空。已有玩家先把当前排名、评分抄到上次字段，再写入新值，并刷新 `dataUpdatedAt`。本次没出现在截图里的玩家保持不动。
- [ ] **P11** 同一事务写入 `import_batches`。原图保存到 `imports/{userId}/{clubId}/{uuid}`。事务失败时人员保持原状，并删掉本次刚保存的原图。成功响应 `{ rowCount, updatedAt }`。

### M4 列表与下线

- [ ] **P12** `GET /api/v1/members`。支持 `clubId`、`keyword`（玩家名称包含，不区分大小写）、`sort`、`order`。默认 `rank asc`。`sort` 只允许九个展示列，非法值 400。空值排在最后。入会时间按原文排序。
- [ ] **P13** 响应带九列、`dataUpdatedAt`、`rankChange`、`scoreChange`。没有上次值、评分为空无法比较、或差值为 0 时，对应变化字段为 `null`。排名数字变小为 `up`，评分变大为 `up`。
- [ ] **P14** 从 `AppModule` 去掉任务、模板、记录、对话、导出和任务资源的控制器。保留 auth、storage、OCR client。旧表不删。
- [ ] **P15** 侧栏改为「俱乐部管理」，子菜单：创建俱乐部 `/clubs`、导入人员 `/imports`、人员列表 `/members`。`/` 和登录成功后进入 `/clubs`。
- [ ] **P16** 创建俱乐部页：名称、会长表单，加上俱乐部表格的编辑和删除。沿用浅蓝色 Element Plus。
- [ ] **P17** 导入页：未选俱乐部时不能上传；选图后立即提交；成功提示写入条数；失败展示接口错误，不清空已有列表数据。
- [ ] **P18** 人员列表页：俱乐部下拉、玩家名称关键字、`el-table` 九列。排名和评分列在有变化时显示箭头和差值。表头排序向 `sort`、`order` 重新请求。
- [ ] **P19** 去掉任务、模板页面和菜单。访问 `/tasks`、`/tasks/new`、`/tasks/:id`、`/templates` 时进入 `/clubs`，不再渲染旧页面。
- [ ] **P20** 用 `assets/微信图片_20261010140035_72.jpg` 走一遍：建俱乐部、导入、列表筛选和排序、再导入一次以检查升降。OCR 服务需已启动。

## 依赖顺序

```text
P1 → P2 → P3
P1 → P4 → P5 → P6
P2 + P6 → P7 → P8 → P9 → P10 → P11
P10 → P12 → P13
P13 + P3 → P15 → P16
P11 → P17
P13 → P18
P15 → P19
P16 + P17 + P18 + P19 → P20
```

P14 可以在 P11、P13 完成后、P20 之前任何时间做。它不依赖页面，但要在端到端验收前完成，否则旧接口还在。

## 人力与并行

一个人时按 P1 → P6 → P11 → P13 → P19 → P20 推进，中间把 P14 插在页面联调之前。

两个人时可以分开：

| 人 | 任务 | 汇合点 |
|---|---|---|
| 甲 | P1–P3，然后 P7–P13、P14 | P6 完成后甲才能做导入 |
| 乙 | P4–P6；P2 的响应形状定下后做 P15、P16 | P11、P13 完成后乙做 P17、P18 |

P20 由一个人从头点到尾，另一人看导入条数和升降是否与库里的上次值一致。

## MVP 范围

本版要一次做完梳理版里的 Must，以及设计里已经写明的失败行为。

| 纳入本版 | 对应 |
|---|---|
| 三个子菜单和俱乐部增删改查 | UC-01、UC-02、UC-03 |
| 选俱乐部、上传、OCR、自动入库、更新时间 | UC-04 |
| 筛选、九列、升降、表头排序 | UC-05、UC-06、UC-07 |
| 任务和模板下线 | UC-08 |
| 导入失败不写半截数据，成功告知条数 | 梳理版 Should，技术设计已定为 422/502 和 `rowCount` |

不纳入本版：

- 职位、分组、当前状态的保存和展示
- 人员手工新增、编辑、删除
- 入会时间从「26天」换算成日期或时长
- 删除旧的任务数据表
- 玩家改名后的身份合并

## 风险与缓冲

| 风险 | 出现在 | 缓冲 |
|---|---|---|
| 样例图是深色游戏界面，OCR 行对不齐列 | P4、P20 | M2 与 M3 之间留 1 天，只调聚类和列边界，不改页面 |
| 本地 OCR 容器没启动，P20 无法导入 | P8、P20 | P20 开始前先看 `/health`。服务不可用时，P8 的 502 仍要测到，样例图验收顺延 |
| 职位两行字把一名玩家拆成两行 | P5 | 单测里放一条没有玩家名称的职位行，确认被丢弃 |
| 旧菜单或默认路由仍指向任务 | P15、P19 | P20 的检查单包含直接打开四个旧地址 |

缓冲用完仍无法从样例图得到玩家名称和排名时，停止继续加页面功能，先把 P6 的失败样例补齐并回到列对齐。不要改成由模型编造缺失数字。
