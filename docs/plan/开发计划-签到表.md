# 开发计划 · 签到表

依据 [需求梳理版](../detail/需求-签到表-梳理版.md) 和 [技术设计](../design/技术设计-签到表.md)。本计划只排期和拆任务，不改代码。

企业微信团队按技术设计处理：全站一套内部应用，Secret 只放环境变量。俱乐部归入这个团队。一场活动可多选俱乐部，发布时校验团队一致。

## 里程碑

一人按顺序做，大约 6 个工作日。企业微信可信域名上的真机收发不挤进这 6 天，另留 1 天，等域名和 IP 白名单就绪后再做。

| 里程碑 | 完成标准 | 建议工期 |
|---|---|---|
| M1 表结构可用 | 活动、绑定、签到、通知表已迁移；未配置企业微信时，现有俱乐部和人员接口仍可用 | 1 天 |
| M2 活动可发布 | 管理员能发布多俱乐部活动并结束；发送失败时活动仍在，且有通知记录 | 1.5 天 |
| M3 绑定与签到 | 玩家令牌下可绑定一个角色并签到；人员列表能看出是否绑定 | 1.5 天 |
| M4 提醒可触发 | 到点只提醒已绑定且属于本场俱乐部的人；每场自动提醒只占一次 | 1 天 |
| M5 页面可用 | 后台可发布和查看签到；人员列表有新列；企业微信活动页能按状态展示 | 1 天 |

M2 结束可以在接口层发布活动，即使企业微信拒收。M3 结束签到主路径的规则已经固定。M5 结束才算管理员和玩家都能从页面走完。真机收到卡片不作为 M2 的完成标准。

## 任务拆分

### M1 数据与团队

- [ ] **P1** Prisma 增加 `wecom_teams`、`activities`、`activity_clubs`、`activity_recipients`、`wecom_bindings`、`activity_check_ins`、`activity_notifications`，以及活动状态、接收人类型、通知类型这些枚举。`clubs` 增加 `wecomTeamId`。
- [ ] **P2** `wecom_bindings` 保证「团队 + 企业微信 userid」唯一，且 `memberId` 唯一。`activity_check_ins` 以活动 + 人员为主键，同一活动下的企业微信 userid 也唯一。删除人员时级联删除绑定和该人员的签到。
- [ ] **P3** 应用启动时，若 `WECOM_CORP_ID`、`WECOM_AGENT_ID`、`WECOM_SECRET`、`WEB_ORIGIN` 齐全，则写入或更新唯一团队，并把 `wecomTeamId` 为空的俱乐部填上。未配置时不插入团队，不阻断现有俱乐部和人员功能。Secret 不入库。
- [ ] **P4** 新建俱乐部时，若唯一团队已存在，写入该 `wecomTeamId`。删除俱乐部前若仍被活动引用，返回 409。

### M2 发布与企业微信发送

- [ ] **P5** `wecom` 模块：缓存 access_token，按企业微信返回的有效期提前刷新。未配置时相关接口返回「企业微信未配置」，且不创建活动。
- [ ] **P6** `GET /api/v1/wecom/audience` 读取当前应用可见范围，返回部门、标签、成员。拿不到部门名称时返回部门 ID。
- [ ] **P7** 文本卡片发送。说明包含活动标题所用的俱乐部名称和开始时间，链接为 `{WEB_ORIGIN}/a/{activityId}`，按钮为「去签到」。说明超长时截断俱乐部名称。
- [ ] **P8** `POST /api/v1/activities`。校验标题、至少一个本人的俱乐部、开始时间、接收范围至少一种、提醒时间为空或晚于当前时间。俱乐部须属于同一 `wecomTeamId`。别人的俱乐部返回 404。同一事务写入活动、俱乐部关联和接收范围，状态为 `PUBLISHED`。
- [ ] **P9** 事务提交后再发发布卡片，并写 `activity_notifications`。企业微信拒收或超时时活动保持已发布，通知记为 `FAILED`。配置缺失时不走这一步，直接在 P8 之前失败且不落活动。
- [ ] **P10** `GET /api/v1/activities` 与 `GET /api/v1/activities/:id` 只返回当前用户的活动。`POST /api/v1/activities/:id/end` 将状态改为 `ENDED` 并写入 `endedAt`。已结束再次调用仍返回已结束。

### M3 绑定、签到与人员列

- [ ] **P11** OAuth 起点与回调。`state` 使用签名并带上活动 ID。回调用 `code` 换 userid，签发玩家令牌。令牌类型与管理员 JWT 区分，不能访问 `/clubs`、`/members`、`/activities` 的管理接口。
- [ ] **P12** `GET /api/v1/player/activities/:id` 返回 `phase`：`unbound`、`ready`、`other_club`、`closed`。未绑定的候选角色只来自本场已选俱乐部，且排除已被占用的角色，并带上俱乐部名称。
- [ ] **P13** `POST /api/v1/player/activities/:id/binding`。角色不属于本场、已被占用，或该企业微信成员已有绑定，返回 409，不覆盖原绑定。活动已结束时返回 409。
- [ ] **P14** `POST /api/v1/player/activities/:id/check-in`。仅 `PUBLISHED` 且绑定角色属于本场俱乐部时写入。重复请求返回原来的 `checkedAt`，不新增行。未绑定、`other_club`、已结束返回 409。`startsAt` 不参与判断。
- [ ] **P15** `GET /api/v1/activities/:id/check-ins` 按本场当前人员列出玩家名称、所属俱乐部、`notifyBound`、`checkedIn`、`checkedAt`。未签到的 `checkedAt` 为空。未选中的俱乐部不出现。
- [ ] **P16** `GET /api/v1/members` 增加 `notifyBound`。`sort=notifyBound` 可用，升序时未绑定在前。新增和编辑请求若带该字段，按现有白名单拒绝。
- [ ] **P17** `DELETE /api/v1/members/:id/wecom-binding` 只删除绑定。未绑定时返回已是未绑定，人员行和已有签到保留。删除人员仍走原接口，绑定因级联一起去掉。导入和编辑不得清除绑定。

### M4 提醒与再次发送

- [ ] **P18** 使用 `@nestjs/schedule` 每分钟扫描。条件为已发布、`remindAt` 已到、`remindClaimedAt` 为空。先用条件更新占住 `remindClaimedAt`，再发送。
- [ ] **P19** 自动提醒的接收人是已绑定、且角色属于本场已选俱乐部的企业微信 userid，不用发布时的部门或标签。没有这样的人时记 `SENT`，接收人数为 0。
- [ ] **P20** 自动提醒失败只记 `FAILED`，不清除占位，定时任务不再重试这场。`remindAt` 为空的活动不进入扫描。
- [ ] **P21** `POST /api/v1/activities/:id/notifications`，`kind` 为 `publish` 或 `remind`。仅已发布可发，已结束返回 409。每次另写一条通知记录。`publish` 使用原接收范围，`remind` 按 P19 重新计算接收人。

### M5 页面

- [ ] **P22** 侧栏「俱乐部管理」增加「活动签到」，路由 `/activities`。列表显示标题、俱乐部名称、开始时间、状态。
- [ ] **P23** 新建对话框：多选本人的俱乐部、标题、开始时间、提醒时间可空、部门 / 标签 / 成员至少选一种。选项来自 `GET /wecom/audience`。未配置企业微信时不提交，并说明原因。
- [ ] **P24** 行内可结束活动、再次发送发布卡片或提醒。签到情况页 `/activities/:id` 用 `el-table` 显示玩家名称、所属俱乐部、是否绑定通知、是否已签到、签到时间。
- [ ] **P25** 人员列表在「入会时间」和「操作」之间增加「是否绑定通知」，显示已绑定或未绑定，表头排序传 `notifyBound`。已绑定行可解除绑定。新增和编辑表单不加该字段。
- [ ] **P26** `/a/:id` 为公开路由，不套 `AppShell`，不读取 `ocr_token`。玩家令牌放在单独的 `sessionStorage` 键。窄屏展示四种 `phase`：选角色、签到、已签到时间、已绑定其他俱乐部的说明。非企业微信打开时提示无法识别身份。

## 依赖顺序

```text
P1 → P2 → P3 → P4
P3 → P5 → P6 → P7
P4 + P7 → P8 → P9 → P10
P5 → P11 → P12 → P13 → P14
P2 + P14 → P15
P2 → P16 → P17
P9 → P18 → P19 → P20 → P21
P6 + P10 → P22 → P23 → P24
P16 + P17 → P25
P11 + P12 + P13 + P14 → P26
```

P16 可以在 P8 之前做，它只依赖绑定表。P22 要等活动列表的字段定下来。P26 要等玩家接口的 `phase` 定下来。

## 人力与并行

一个人时按 M1 → M2 → M3 → M4 → M5 推进。P16、P17 放在 P14 之后、页面之前，避免人员列表先接上一个还会改的字段。

两个人时可以分开：

| 人 | 任务 | 汇合点 |
|---|---|---|
| 甲 | P1–P10，然后 P18–P21 | P7 完成后才能发布 |
| 乙 | P11–P17；P10 的响应定下后做 P22–P25 | P14 完成后乙做 P26 |

真机收发由一个人在可信域名上走发布、点卡片、绑定、签到、提醒。另一人对照通知记录里的成功或失败。

## MVP 范围

本版做完梳理版里的 Must，以及技术设计已经写明的 Should 和失败行为。

| 纳入本版 | 对应 |
|---|---|
| 多选同一企业微信团队下的俱乐部并发布 | UC-01、验收 1 |
| 按部门、标签或成员发可点击卡片 | UC-02、验收 2 |
| 提醒时间可空；到点提醒已绑定人员 | UC-03、验收 9、Q1 |
| 绑定一个未被占用的角色 | UC-04、验收 3、4 |
| 发布后签到，每场一次，不看开始时间 | UC-05、验收 5、6、7 |
| 人员列表「是否绑定通知」 | UC-06、验收 8 |
| 按活动查看各俱乐部签到情况 | UC-07、Q5 |
| 管理员解除绑定；删除人员时去掉绑定 | UC-08、Q3、Q4 |
| 发送失败可再发；结束活动后不能再签 | UC-09、Q2 |

不纳入本版：

- 按「是否绑定通知」筛选人员
- 活动二维码、个人微信扫码
- 企业微信团队的创建和切换页面
- 一个俱乐部加入多个团队，或一场活动跨团队
- 玩家自己换绑
- 通讯录全量同步、企业微信打卡
- Redis、BullMQ
- 跨活动的人员签到总表

## 风险与缓冲

| 风险 | 出现在 | 缓冲 |
|---|---|---|
| 本地没有可信域名，点不开真实卡片 | P7、P11、P26 | 功能工期里用接口核对发布、绑定、签到和提醒规则。真机另留 1 天，排在域名和 IP 白名单完成之后 |
| 企业微信拒收部分可见范围外成员 | P9、P21 | 活动保持已发布，通知记失败。页面上要能看到失败说明和再次发送 |
| 两人同时绑定同一角色 | P13 | 靠唯一约束返回 409。活动页收到冲突后重新请求候选角色 |
| 定时任务在企业微信已收到消息后超时 | P20 | 不自动重试。只允许管理员手动再发 |
| 未配置企业微信时俱乐部页面被迁移拖垮 | P3、P4 | 启动回填失败不得影响现有俱乐部和人员接口。发布接口单独返回未配置 |
| 多开 API 进程重复提醒 | P18 | 用 `remindClaimedAt` 条件更新占位，不用内存锁 |

可信域名未就绪时，不停下 M1–M5。先完成接口和页面，真机验收顺延到缓冲那一天。
