# 开发计划 · 俱乐部数据采集

依据 [需求梳理版](../detail/需求-俱乐部数据采集-梳理版.md)、[技术设计](../design/技术设计-俱乐部数据采集.md)。**本计划只拆任务**；改代码须另开实现任务。

## 里程碑

一人按顺序做，大约 **1.5 个工作日**。公开读接口定稿后，后台页面和 Guide 排行页可以并行。

| 里程碑 | 完成标准 | 建议工期 |
|---|---|---|
| **M1 当前榜与公开读** | Guide 库有 `club_ranking_current`；无数据时 `GET /club-rankings` 返回 `{ clubs: [] }` | 0.5 天 |
| **M2 写入** | 超管经 `apps/api` 写入；guide-api 校验失败不覆盖；再次上传只留新的一份 | 0.5 天 |
| **M3 后台采集页** | 系统管理出现「俱乐部数据采集」；角色不可勾选；页面解析 JSON 并只提交 `clubs` | 0.5 天 |
| **M4 Guide 排行页** | 首页卡片进入 `/club-rankings`，六列按 `rank` 展示；无数据时「暂无排行」 | 与 M3 并行，0.5 天 |

**MVP 发布线**：M1 → M2 →（M3 与 M4 并行）。M4 只依赖公开读，不依赖采集页。

## MVP 与用例对齐

| 用例 | 里程碑 | 任务 |
|---|---|---|
| UC-01 仅超管、不可分配、直链进不去 | M3 | C7、C8 |
| UC-02 解析并上传，提示条数 | M2 + M3 | C5、C6、C9 |
| UC-03 非法文件不覆盖 | M2 + M3 | C2、C5、C9 |
| UC-04 首页入口 | M4 | C12 |
| UC-05 六列、按 rank | M1 + M4 | C4、C11 |
| UC-06 再次上传覆盖 | M2 | C5 |
| UC-07 暂无排行 | M1 + M4 | C4、C11 |

图片识别、历史榜、签到俱乐部打通、角色授权都不在本计划。

## 任务拆分

### M1 当前榜与公开读

- [ ] **C1** `prisma/guide/schema.prisma` 增加 `ClubRankingCurrent`：`id`、`clubs Json`、`updatedAt`，表名 `club_ranking_current`。新增迁移。只改源 schema，不手改 `apps/guide-api/src/generated`。
- [ ] **C2** `packages/guide-types` 增加 `ClubRankingRow`、`ClubRankingDto`，以及 `normalizeClubRankingClubs`。规则与技术设计 §4.1 一致：1～200 条；六字段；首尾空白去掉后非空、最长 64；整数且在范围内；`rank` 不重复；结果按 `rank` 升序。失败返回可读原因，不抛未捕获异常。从包入口导出。
- [ ] **C3** `apps/web` 增加对 `@ocr/guide-types` 的依赖，`predev` / `prebuild` 先构建该包。采集页与两个 API 都调用 C2，避免三套校验。
- [ ] **C4** `apps/guide-api` 新增 `GET /club-rankings`，无鉴权。无行时 200，`clubs` 为 `[]`。有行时原样返回已排序的数组。不返回 `updatedAt`。在 `app.module` 挂上模块。

### M2 写入

- [ ] **C5** `PUT /admin/club-rankings`，沿用 `GuideAdminTokenGuard`。先 `normalizeClubRankingClubs`，失败 400 且不 `upsert`。成功写入 id `current`，响应 `{ count }`。空数组、超过 200、缺字段、重复 `rank` 都走这条失败路径。
- [ ] **C6** `apps/api` 新增 `POST /club-rankings`。登录 JWT，且 `user.isSuper`，否则 403。不用 `RequireMenu`。通过后再校验，然后用 `GUIDE_ADMIN_TOKEN` 调用 C5。Token 缺失 503，Guide API 连不上 502，与 `WikiAdminService` 相同。成功把 `{ count }` 交回浏览器。在 `app.module` 注册模块。不引用 clubs / members 服务。

### M3 后台采集页

- [ ] **C7** `packages/shared-types`：系统管理增加 `club-ranking-import` / 「俱乐部数据采集」/ `/club-ranking-import`。新增 `SUPER_ONLY_MENU_KEYS`。`apps/api` 的 `cleanMenus` 见到该 key 返回 400。`Roles.vue` 的可勾选列表去掉它（与现有「始终可见」菜单同一处过滤）。
- [ ] **C8** `apps/web/src/router.ts` 增加子路由，`meta.menu = 'club-ranking-import'`。侧栏仍只渲染接口返回的菜单：超管能看见，普通角色打开该地址回到已有菜单。
- [ ] **C9** `ClubRankingImport.vue`：选择 `.json`，`JSON.parse`，只取 `clubs` 交给 C2。解析失败或校验失败时说明原因，不发请求，并显示将上传的行数。成功后提示「已写入 N 条」。`client.ts` 增加对应 POST。

### M4 Guide 排行页

- [ ] **C10** `apps/guide/src/app/club-rankings/page.tsx` 与 `club-rankings.css`。`guideFetch('/club-rankings', { cache: 'no-store' })`。标题固定「俱乐部排行」。六列：排名、俱乐部、区服、会长、人数、评分。`rank` 为 1、2、3 的行强调名次。评分千分位，库存值不变。深色底，窄屏横向滚动。不嵌 `rank.png`，不显示二维码、更新时间、`rawText`。
- [ ] **C11** `clubs` 为空时表格区显示「暂无排行」。请求失败时说明暂时无法加载。
- [ ] **C12** 首页 `FEATURES` 增加「俱乐部排行」→ `/club-rankings`，`enabled: true`，插在「敬请期待」之前。不加顶栏。

### 明确不做

- 读取或识别 `docs/俱乐部数据/rank.png`。
- 保存或展示 `clubs` 以外的 JSON 字段，包括 `capturedAt`。
- 排行历史、名次升降、搜索筛选。
- 写入 OCR 库的俱乐部或人员。
- 把该菜单分配给普通角色，或放进登录后人人可见的菜单。

| 人 | 任务 | 汇合点 |
|---|---|---|
| 甲 | C1、C2、C4、C5、C6 | C2 的字段名和 400 原因定稿后，乙才能做 C9 |

## 风险与缓冲

| 风险 | 缓冲 |
|---|---|
| 浏览器和两个 API 各写一套校验，边界不一致 | 只维护 C2。页面和接口都调用它，不在 Vue 里再写一份数字范围 |
| `GUIDE_ADMIN_TOKEN` 或 Guide API 没起来，上传 503 | C6 对照现有 Wiki 代理。核对写入前先确认 Guide API 健康，失败用例看响应码，不改库 |
| 排行页沿用 60 秒缓存，刚上传仍是旧榜 | C10 写明 `no-store`，不改 `guideFetch` 的默认缓存 |
| 超管菜单漏进角色勾选 | C7 同时改目录、`cleanMenus` 和角色页。写入仍只认 `isSuper` |

## 完成定义

1. 梳理版验收 1～6 都有对应任务：C7～C9、C5～C6、C12、C10、C5 的覆盖写入、C4+C11、且 C6 不调用签到俱乐部接口。
2. 实现完成时核对这几个接口是否与技术设计 §6 一致：无数据的 `GET /club-rankings`；带管理凭证的 `PUT /admin/club-rankings`（样例 `clubs` 应得到 `count: 50`）；空 `clubs` 为 400 且再次 `GET` 仍是上一份；非超管 `POST /club-rankings` 为 403。不写自动化测试，不做页面走查。界面由使用方自行看。
3. OCR 的 `Club`、`Member` 模型无 diff。
