# 开发计划 · 新增后台账号+角色管理

依据 [需求梳理版](../detail/需求-新增后台账号+角色管理-梳理版.md) 和 [技术设计](../design/技术设计-新增后台账号+角色管理.md)。本计划只排期和拆任务，不改代码。

一个账号只属于一个角色。菜单键放在共享类型里。`POST /api/v1/permission` 只返回菜单。俱乐部、人员、导入和活动改为按角色绑定的俱乐部过滤。停用已有账号只做一次迁移。

## 里程碑

一人按顺序做，大约 5 个工作日。

| 里程碑 | 完成标准 | 建议工期 |
|---|---|---|
| M1 表结构可用 | 角色、菜单绑定、俱乐部绑定已迁移；已有账号均为停用；现有俱乐部数据仍在 | 0.5 天 |
| M2 能登录并拿到菜单 | 配置了环境变量就能用超级管理员登录；`POST /permission` 返回全部菜单；停用账号和注册接口都不可用 | 1 天 |
| M3 账号和角色可维护 | 超级管理员能增删改账号和角色，并绑定菜单与俱乐部；越权修改超级管理员被拒绝 | 1 天 |
| M4 数据范围切换 | 普通角色只看到已绑定俱乐部及其人员、导入、活动；新建俱乐部自动进入创建者角色 | 1.5 天 |
| M5 页面可用 | 侧栏来自权限结果；账号页和角色页可用；注册入口去掉 | 1 天 |

M2 结束时超级管理员已能从接口拿到菜单和全部俱乐部，但普通角色的数据范围还没改完。M4 结束才算可见范围切换完成。M5 结束才算从页面走完创建角色、创建账号、按菜单登录。

## 任务拆分

### M1 数据与菜单目录

- [ ] **P1** Prisma 增加 `roles`、`role_menus`、`role_clubs`。`users` 增加可空 `roleId` 和 `disabled`（默认 false）。`roles.name` 唯一。`role_menus` 以角色 + 菜单键为主键。`role_clubs` 以角色 + 俱乐部为主键。删除角色时级联删除两种绑定。删除俱乐部时级联删除 `role_clubs`。
- [ ] **P2** 一次性迁移：已有用户全部 `disabled = true`，`roleId` 留空。这段逻辑放在迁移里，不放进每次启动。`clubs.userId` 和 `clubs(userId, name)` 唯一约束保持不变。
- [ ] **P3** 在 `packages/shared-types` 写固定菜单目录。子菜单键为 `clubs`、`imports`、`members`、`activities`、`accounts`、`roles`，并带标题、路径和父级 `club-management` 或 `system`。父级没有独立路径。

### M2 登录、超级管理员与菜单接口

- [ ] **P4** 增加环境变量 `SUPER_ADMIN_EMAIL`、`SUPER_ADMIN_PASSWORD`，并写进 `.env.example`。API 启动时保证存在名为「超级管理员」、`isSuper = true` 的角色，并写入全部子菜单键。
- [ ] **P5** 两个变量都有值时，按邮箱查找用户。不存在则创建启用账号，密码按现有方式哈希，角色为超级管理员。已存在则只启用并挂上该角色，不覆盖密码。变量缺失时记录错误，不创建账号。启动时不修改其他用户的 `disabled`。
- [ ] **P6** 登录时用户不存在、密码不对或已停用，都返回 401，文案仍是「邮箱或密码不正确」。JWT 载荷仍只有用户 id 和邮箱。之后每个管理端请求重新读用户，不存在或已停用则 401。`typ = wecom` 的玩家令牌不读 `users`。
- [ ] **P7** 去掉 `POST /auth/register`。
- [ ] **P8** `access`：超级管理员的可见俱乐部为全部；普通角色读 `role_clubs`；没有角色时为空。能判断当前用户是否持有某个子菜单键。`isSuper` 的菜单不查 `role_menus`。
- [ ] **P9** `POST /api/v1/permission` 无正文。超级管理员返回两棵完整目录。普通角色只返回已绑定的子菜单，没有子项的父级省略。没有角色时返回 `{ "menus": [] }` 且状态 200。响应不含俱乐部 id。未带有效 JWT 或账号已停用时 401。

### M3 账号与角色

- [ ] **P10** `GET / POST / PATCH / DELETE /api/v1/accounts`。写操作要求菜单键 `accounts`，否则 403。创建要求邮箱、8 至 72 位密码和一个非超级管理员角色，默认启用。邮箱转小写，重复返回 409。列表支持可选查询 `email`，返回邮箱、名称、停用状态、角色 id 和角色名称，不返回密码哈希。
- [ ] **P11** 修改账号时密码省略或空字符串表示不改。不能删除自己，不能停用自己，不能删除超级管理员，不能改超级管理员的角色或停用状态，不能把任何账号改成超级管理员角色，以上返回 409。启用 `roleId` 为空的历史账号时必须同时带上角色，否则 400。删除账号不删除其创建的俱乐部。
- [ ] **P12** `GET / POST / PATCH / DELETE /api/v1/roles`。`POST`、`PATCH`、`DELETE` 要求菜单键 `roles`，否则 403。名称去空格后非空且唯一，重名 409。`menuKeys` 只能是 P3 的子菜单键，未知键 400。`clubIds` 去重。
- [ ] **P13** `GET /roles` 在持有 `accounts` 或 `roles` 时允许。仅持有 `accounts` 时，结果去掉超级管理员角色。超级管理员调用时能看到该角色，但 `PATCH` 和 `DELETE` 仍返回 409。
- [ ] **P14** 普通操作者保存角色时，`clubIds` 必须都在自己的可见俱乐部内，否则 400。只替换他能看见的绑定，看不见的原绑定保留。超级管理员按请求全量替换 `role_clubs`。删除仍有账号使用的角色返回 409，不改这些账号的 `roleId`。列表含菜单数量和俱乐部数量。

### M4 俱乐部、人员与活动的可见范围

- [ ] **P15** 俱乐部列表、修改、删除改为 `access` 的可见范围。范围外的单条返回 404。列表带上创建人邮箱，便于超级管理员区分同名俱乐部。
- [ ] **P16** 新建俱乐部与写入创建者角色的 `role_clubs` 放在同一事务。超级管理员创建时也写这一行。其他角色没有这行就看不到。
- [ ] **P17** 人员列表、新增、编辑、删除、解除绑定、按俱乐部导入，改为俱乐部必须可见。未指定俱乐部的人员列表只含可见俱乐部。
- [ ] **P18** 活动列表、详情、结束、签到情况、再次发送改为：该活动的全部已选俱乐部都在可见范围内才可见，缺一个则整场 404。发布时每个俱乐部都必须可见。`activities.userId` 仍写入创建人，但不再用来过滤。
- [ ] **P19** 任务、模板等旧接口继续按创建人过滤。玩家活动页和玩家令牌不读角色，也不调用 `/permission`。

### M5 页面

- [ ] **P20** 删除注册页和登录页上的注册入口。`/register` 不再打开注册表单。
- [ ] **P21** 登录成功后请求 `POST /permission`。菜单放在登录状态旁，不写入存放 JWT 的 `localStorage` 键。`AppShell` 挂载时重新请求。退出时清掉。
- [ ] **P22** 侧栏按返回的树渲染，包含窄屏。不再写死俱乐部管理下的四项。
- [ ] **P23** 后台路由带上菜单键。`/activities/:id` 使用 `activities`。权限尚未返回时等待这一次请求。目标键不在结果里则进入结果中的第一个路径。结果为空时留在壳内，主区域说明当前没有可用菜单，不跳到 `/clubs`。
- [ ] **P24** `/accounts`：表格展示邮箱、名称、角色、状态。可新建、编辑、停用或启用、删除。编辑时密码可留空。角色下拉来自 `GET /roles`。
- [ ] **P25** `/roles`：表格展示名称、菜单数量、俱乐部数量。编辑时按固定目录勾选菜单，按当前用户可见的俱乐部勾选绑定。超级管理员角色不提供保存和删除。

## 依赖顺序

```text
P1 → P2 → P3
P3 → P4 → P5
P1 → P6 → P7
P5 + P6 → P8 → P9
P8 + P9 → P10 → P11
P8 → P12 → P13 → P14
P8 → P15 → P16
P15 → P17 → P18
P18 → P19
P7 + P9 → P20 → P21 → P22 → P23
P11 + P14 + P15 → P24 → P25
```

P6 可以和 P4 并行，它只依赖用户表上的 `disabled`。P17、P18 要等可见范围的判断定下来。P24 要等账号接口和角色列表的字段定下来。

## 人力与并行

一个人时按 M1 → M2 → M3 → M4 → M5 推进。M4 会改到现有俱乐部、人员和活动查询，放在账号接口之后，避免一边改可见范围一边还没有角色可绑。

两个人时可以分开：

| 人 | 任务 | 汇合点 |
|---|---|---|
| 甲 | P1–P9，然后 P15–P19 | P8 完成后乙才能做账号和角色 |
| 乙 | P10–P14；P9 的菜单形状定下后做 P20–P23 | P14 和 P15 都完成后乙做 P24、P25 |

甲先给乙一份 `/permission` 的响应样例，以及可见俱乐部的判断方式。乙不在甲改完 P18 之前把活动页的筛选假设写成「只看创建人」。

## MVP 范围

本版做完梳理版里的 Must，以及技术设计已经写明的 Should。

| 纳入本版 | 对应 |
|---|---|
| 环境变量预置超级管理员，看到全部菜单和全部俱乐部 | UC-01、验收 1、Q1 |
| `POST /permission` 带 JWT，只返回菜单 | UC-02、验收 3 |
| 账号增删改查，一账号一角色 | UC-03、验收 4 |
| 停用、再次启用、编辑时改密码 | UC-04、UC-10、验收 5 |
| 角色绑定固定菜单和俱乐部 | UC-05、Q3、Q4、Q5 |
| 人员、导入、活动跟随俱乐部绑定 | UC-06、验收 6 |
| 新建俱乐部自动绑到创建者角色 | UC-07、验收 7、8 |
| 没有菜单不能进对应页面；账号和角色写接口校验菜单键 | UC-08 |
| 迁移停用已有账号，且可再次启用 | UC-09、验收 2 |
| 不能删除或停用自己，不能改超级管理员 | 验收 9、Q2、Q6 |
| 改角色后下次请求生效 | Q7 |
| 无菜单可以登录，侧栏为空 | Q8 |
| 关闭自助注册 | 验收 10 |

不纳入本版：

- 一个账号多个角色
- `/permission` 返回俱乐部或另外的权限码
- 菜单目录本身的增删改
- 忘记密码、邮件重置密码
- 玩家签到改走后台角色
- 把任务、模板改成按角色过滤
- 每次启动重新停用非超级管理员
- 按「是否绑定通知」之外的新筛选

## 风险与缓冲

| 风险 | 出现在 | 缓冲 |
|---|---|---|
| 迁移已把旧账号停用，但环境变量还没配 | P2、P5 | 部署前先写好 `SUPER_ADMIN_EMAIL` 和 `SUPER_ADMIN_PASSWORD`。变量缺失时只记错误，不打开注册 |
| 重启后又把已启用账号停掉 | P2、P5 | 停用只写在迁移中。启动只处理超级管理员这一行，代码评审时对照这一点 |
| 活动跨了未绑定俱乐部，签到列表带出别的人员 | P18 | 缺一个俱乐部则整场 404。自测里用两个俱乐部各绑一个角色核对 |
| 普通角色保存时覆盖了自己看不见的俱乐部绑定 | P14 | 只替换可见部分。自测先用超级管理员绑一个该角色看不见的俱乐部，再让普通角色保存 |
| 可见范围改完后，创建人看不到自己刚建的、但未绑定的数据 | P16、P18 | 新建俱乐部必须和 `role_clubs` 同一事务。活动改为按俱乐部可见，不再按 `activities.userId` |
| 历史账号没有角色就被启用 | P11 | 启用请求没有 `roleId` 时返回 400 |
| 同名俱乐部在超级管理员列表里分不清 | P15 | 列表带创建人邮箱。不改名称唯一规则 |

M4 比其他里程碑多半天，用来核对人员导入和活动详情这两条已经上线的路径。环境变量未就绪时不停下 M1，但 M2 的完成标准要等到变量配上之后才算通过。
