# 需求梳理 · 招聘需求

公开申请页收集入会意向，已登录后台在「招聘管理」里查看并标记处理结果。同意或不同意只改申请状态，不写入人员列表。

源需求写的是「工会」。当前产品里对应的组织是「俱乐部」（名称、会长，挂在俱乐部管理下）。本版把申请表上的「希望加入的工会」暂定为从现有俱乐部名单里选择。

## 产品定位

两块独立入口：

- **申请人**：不登录，打开单独页面填写申请。页面不进管理侧栏，视觉沿用后台的浅蓝色 Element Plus。
- **管理员**：登录后从新菜单进入申请列表，按是否看过详情区分未读和已读，并记录同意或不同意。

申请数据与人员表分开。人员列表的增删改、导入、名次和评分变化都不受本申请结果影响。

## 用户与用例

| ID | 优先级 | 用例 | 验收要点 |
|---|---|---|---|
| UC-01 | Must | 打开公开申请页 | 不登录即可访问；不出现在管理菜单和 `AppShell` 侧栏中 |
| UC-02 | Must | 看到欢迎语 | 页面展示「无忧大家庭欢迎你的加入~」 |
| UC-03 | Must | 填写并提交申请 | 游戏名称、非凡评分、uid、希望加入的工会、选择无忧的理由五项都必填；缺任一项不能提交成功 |
| UC-04 | Must | 选择工会 | 下拉选项来自不带登录凭证的俱乐部列表接口；无俱乐部时不能选出有效工会，提交失败并给出反馈 |
| UC-05 | Must | 看到提交结果 | 成功或失败都在页面上有明确反馈；失败时已填内容保留 |

| UC-09 | Must | 查看申请详情 | 详情包含五项申请内容和提交时间，以及当前已读状态、处理状态 |

## 功能拆解

### 公开申请页

独立路由，不要求登录，不套管理布局。配色、按钮、表单控件与后台一致（现有浅蓝色 Element Plus）。

| 字段 | 规则 |
|---|---|
| 游戏名称 | 必填文本。不与人员表的玩家名称对照，也不要求已在某个俱乐部中 |
| 非凡评分 | 必填，非负整数 |
| uid | 必填文本，按原文保存 |
| 希望加入的工会 | 必填，单选。选项为俱乐部 `id` + 名称，数据来自公开列表接口 |
| 你选择无忧的理由 | 必填文本 |

提交成功后在本页给出成功反馈。提交失败（校验不通过、工会已不存在、网络或服务错误）给出失败原因，表单内容保留，可再次提交。

### 公开俱乐部列表

供申请页使用，请求不携带、也不校验登录凭证。

- 只返回选择所需的俱乐部标识和名称。
- 不返回会长、人员、导入记录或其他管理字段。
- 申请提交时再次按所选标识校验俱乐部仍存在；已删除则拒绝并反馈失败。

### 申请列表

新增大菜单「招聘管理」，其下小菜单「申请列表」。菜单纳入现有角色菜单：超级管理员可见；其他角色需在角色管理中勾选后才可见、才可访问。

列表至少能按未读、已读分开查看。每条展示游戏名称、非凡评分、uid、工会名称、提交时间、已读状态、处理状态。处理状态取「待处理」「同意」「不同意」之一，新申请为待处理。

详情：

- 打开详情时，若当前为未读，则记为已读。已读后保持已读。
- 详情展示全部申请字段、提交时间、已读状态、处理状态。
- 在详情或列表中可以把处理状态改为同意或不同意，两种结果可以互相改。修改只更新这条申请，不新增、不修改、不删除人员列表中的任何行。

申请人不能回看自己的申请，也不能看到同意或不同意。

## 非功能需求

| 项 | 要求 |
|---|---|
| 界面 | 申请页与后台共用浅蓝色主题和 Element Plus 控件；申请页不是管理页 |
| 访问 | 申请页和拉俱乐部列表、提交申请都不需要登录 |
| 管理访问 | 申请列表沿用现有登录和菜单权限，未授权账号不能打开该页或对应接口 |
| 数据隔离 | 申请记录独立存放。同意、不同意、已读都不写人员表 |
| 反馈 | 成功、失败都在申请页可见，失败说明原因 |

## 端到端流程

1. 申请人打开公开申请页，看到欢迎语，并从下拉中选择一个俱乐部。
2. 填完五项后提交。缺项或所选俱乐部已不存在时停留在本页并看到失败反馈。
3. 提交成功后看到成功反馈。后台出现一条未读、待处理的申请。
4. 有菜单权限的管理员打开「招聘管理 / 申请列表」，在未读中看到这条。
5. 打开详情后，该条变为已读，已读列表中能看到，未读列表中不再出现。
6. 管理员标为同意或不同意。再到人员列表查询，原有人员行不变，也不会凭这条申请多出一行。

## 范围

**In**

- 公开申请页：欢迎语、五项必填、提交、成功或失败反馈
- 不校验登录的俱乐部列表，以及提交申请
- 管理端「招聘管理 / 申请列表」
- 未读 / 已读（以是否打开详情为准）
- 待处理 / 同意 / 不同意，且不影响人员列表

**Out**

- 同意后自动写入或更新人员列表
- 按游戏名称或 uid 与现有人员合并、去重、覆盖
- 通知申请人处理结果，或让申请人查询进度
- 编辑已提交的五项内容、删除申请、导出申请
- 验证码、登录后才能申请、企业微信身份
- 修改俱乐部、人员、活动签到、账号角色的既有规则

## 待澄清

| ID | 问题 | 不答复时的暂定 |
|---|---|---|
| Q1 | 「工会」是否就是现有俱乐部？ | 是。下拉使用俱乐部名称，提交保存俱乐部 id |
| Q2 | 公开列表返回哪些俱乐部？俱乐部目前按账号和角色范围可见 | 返回全部俱乐部的 id 和名称，不做登录和角色过滤 |
| Q3 | uid 的格式和是否唯一？ | 任意非空文本，不查重，同一 uid 可多次申请 |
| Q4 | 非凡评分是否必须为整数？ | 非负整数，与人员表评分同一数值范围 |
| Q5 | 未读 / 已读是全局一条状态，还是每个管理员各记各的？ | 记在申请上，任一有权限的人打开详情后，所有人看到的都是已读 |
| Q6 | 已读后能否改回未读？ | 不能 |
| Q7 | 同意和不同意能否改？ | 可以在两者之间改，也可以从待处理改为其中之一。不能改回待处理 |
| Q8 | 列表默认看哪一档？ | 默认未读。提供未读、已读切换，两档都显示处理状态 |
| Q9 | 角色若只被分配了部分俱乐部，申请列表是否只看这些俱乐部？ | 只显示其角色俱乐部范围内的申请；超级管理员看全部 |
| Q10 | 文本长度上限？ | 游戏名称、uid 各 64 字；理由 500 字；超出拒绝并反馈 |
| Q11 | 公开页路径？ | `/apply` |
| Q12 | 成功后表单如何处理？ | 清空表单并显示成功提示，可继续提交下一份 |
| Q13 | 同一人短时间重复提交？ | 允许。每份申请独立成行 |

## 验收标准

1. 未登录打开 `/apply`，能看到「无忧大家庭欢迎你的加入~」，且侧栏没有管理菜单。
2. 工会下拉只含俱乐部名称，对应请求不带登录凭证；接口不返回会长和人员。
3. 五项任一为空不能提交成功，页面给出失败反馈，已填内容还在。
4. 五项合法且工会仍存在时提交成功，页面给出成功反馈；申请列表出现该条，状态为未读、待处理。
5. 提交后所选俱乐部被删除时，再次提交得到失败反馈，不产生新申请。
6. 无「申请列表」菜单的账号看不到「招聘管理」，直接访问申请列表地址也会被挡回其可用菜单。
7. 有权限的账号能在未读中看到新申请；打开详情后该条只出现在已读中。
8. 把申请标为同意或不同意后，状态被记住；人员列表行数和各字段与标记前一致。
