# 技术设计 · 新增后台账号+角色管理

依据 [需求梳理版](../detail/需求-新增后台账号+角色管理-梳理版.md) 的已确认口径，以及 Q1–Q8 的暂定结论。本版只定方案，不改代码。

## 目标与约束

后台账号由超级管理员维护。一个账号只属于一个角色。角色勾选固定菜单，并绑定俱乐部。登录成功后 `POST /permission` 只返回菜单。俱乐部、人员、导入、活动按角色绑定的俱乐部过滤。

沿用现有技术栈：Vue 3、Element Plus、Vue Router、NestJS、JWT、PostgreSQL、Prisma。不新增权限框架。

| 已有能力 | 本需求中的用法 |
|---|---|
| `POST /auth/login` 与 JWT | 继续用邮箱和密码。签发内容仍是用户 id，不把菜单写进令牌 |
| `users` | 增加所属角色和停用标记。关闭 `POST /auth/register` |
| `clubs.userId` | 保留为创建人。列表和读写不再用它做可见范围 |
| `members`、导入、`activities` | 改成跟俱乐部可见范围走 |
| 玩家令牌 `typ=wecom` | 不读角色，不调用 `/permission` |

约束：

- 全局前缀仍是 `/api/v1`。权限接口的完整路径是 `POST /api/v1/permission`，控制器路径为小写 `permission`。
- 菜单键只有一份，放在 `packages/shared-types`。接口校验和前端路由用同一份键，不在数据库里维护菜单目录。
- 超级管理员是角色上的标记，不是一条可勾选的菜单。接口不能创建或取消这个标记。
- 「停用其余已有账号」只在数据迁移时执行一次。服务每次启动只保证超级管理员存在，不再把别人改回停用。
- 任务、模板等旧接口仍按创建人，不接入角色。侧栏不出现这些入口。

## 总体架构

```text
后台浏览器
  登录 → POST /api/v1/permission → 按菜单渲染侧栏
  账号 / 角色 / 俱乐部 / 人员 / 活动
        │  JWT
        ▼
NestJS
  auth        登录、停用校验、拒绝注册
  access      当前用户可见俱乐部、是否超级管理员、是否持有某菜单
  accounts    账号增删改查、停用与启用
  roles       角色增删改查、菜单键与俱乐部绑定
  clubs / members / activities
              可见范围改为 access，不再用创建人
        │
        ▼
PostgreSQL
  users.role_id、users.disabled
  roles、role_menus、role_clubs
```

玩家活动页仍走企业微信令牌和 `/a/:id`，不进入这张图。

## 模块职责

| 模块 | 职责 |
|---|---|
| `packages/shared-types` 菜单目录 | 固定目录、菜单键、标题、路径、父子关系 |
| `auth` | 登录时拒绝停用账号。JWT 校验时重新读用户，停用或不存在则 401。去掉注册 |
| `access` | 解析当前用户的角色。超级管理员的可见俱乐部为全部，普通角色读 `role_clubs`。供俱乐部、人员、活动调用 |
| `accounts` | 账号维护。写操作要求当前用户持有菜单键 `accounts` |
| `roles` | 角色维护。写操作和读取要求菜单键 `roles`。保存菜单键与俱乐部绑定 |
| `clubs` | 列表和读写改为可见俱乐部。新建成功后，把俱乐部写入创建者角色的 `role_clubs` |
| `members`、`activities` | 凡是原先 `club.userId` 或 `activity.userId` 表示「是不是我的」，改为可见俱乐部 |
| Web | 去掉注册页。侧栏改读权限结果。路由按菜单键拦截 |

`access` 不做独立 HTTP 接口。`/permission` 放在 `auth` 或单独的 `permission` 控制器，内部调用 `access` 滤出菜单树。

## 菜单目录

| 键 | 标题 | 路径 | 父级 |
|---|---|---|---|
| `club-management` | 俱乐部管理 | 无，只做目录 | 根 |
| `clubs` | 创建俱乐部 | `/clubs` | `club-management` |
| `imports` | 导入人员 | `/imports` | `club-management` |
| `members` | 人员列表 | `/members` | `club-management` |
| `activities` | 活动签到 | `/activities` | `club-management` |
| `system` | 系统管理 | 无，只做目录 | 根 |
| `accounts` | 账号管理 | `/accounts` | `system` |
| `roles` | 角色管理 | `/roles` | `system` |

`/activities/:id` 使用 `activities`，不单列键。父级没有独立页面。某个父级下一项子菜单都没有时，`/permission` 不返回这个父级。

角色保存时只接受上表子菜单键。传入未知键返回 400。父级键不入库，返回菜单树时按子菜单键归到父级。

## 数据模型

### roles

| 字段 | 类型 | 规则 |
|---|---|---|
| id | uuid | 主键 |
| name | string | 唯一，去空格后非空 |
| isSuper | boolean | 只有预置的超级管理员角色为真。接口不可改 |
| createdAt | 时间 | |

### role_menus

| 字段 | 类型 | 规则 |
|---|---|---|
| roleId | uuid | 外键，删除角色时级联删除 |
| menuKey | string | 与角色组成主键。只能是子菜单键 |

超级管理员角色不依赖这张表判断菜单。`/permission` 对超级管理员直接返回全部目录。迁移时仍写入全部子菜单键，便于对照。

### role_clubs

| 字段 | 类型 | 规则 |
|---|---|---|
| roleId | uuid | 外键，删除角色时级联删除 |
| clubId | uuid | 外键到 `clubs`。俱乐部删除时级联删除此行。与角色组成主键 |

超级管理员能否看到俱乐部，不查这张表。普通角色只看这里的行。

### users 增量

| 字段 | 类型 | 规则 |
|---|---|---|
| roleId | uuid，可空 | 外键到 `roles`。新建账号必填。历史停用账号在补上角色前可以空着 |
| disabled | boolean | 默认 false。true 时不能通过登录和 JWT 校验 |

保留 `email`、`passwordHash`、`name`。`clubs.userId`、`activities.userId`、`import_batches.userId` 继续表示创建人，唯一约束 `clubs(userId, name)` 不变。

已有用户在迁移中全部 `disabled = true`，`roleId` 留空。超级管理员由启动逻辑启用并挂上超级管理员角色，不在这条迁移里写死邮箱。

## 关键流程

### 预置超级管理员

环境变量：

| 变量 | 含义 |
|---|---|
| `SUPER_ADMIN_EMAIL` | 超级管理员邮箱 |
| `SUPER_ADMIN_PASSWORD` | 仅在该邮箱还不存在时，用作初始密码 |

API 启动时：

1. 保证存在名为「超级管理员」、`isSuper = true` 的角色，并写上全部子菜单键。
2. 两个变量都有值时，按邮箱查找用户。没有则创建启用账号，密码按现有方式哈希，角色为超级管理员。已存在则只把 `disabled` 置为 false、`roleId` 设为该角色，不覆盖密码。
3. 变量缺失时不创建账号，并记录错误。不恢复注册接口。

启动逻辑不扫描其他用户，避免每次重启把已经再次启用的账号停掉。

### 登录与令牌

1. 邮箱和密码的校验方式不变。
2. 用户不存在、密码不对、或 `disabled = true`，都返回 401，文案仍是「邮箱或密码不正确」。不单独提示停用。
3. 令牌载荷保持 `sub` 为用户 id、`email`。不写入角色和菜单。
4. 之后每个管理端 JWT 请求重新读用户。用户不存在或已停用则 401。这样停用和改角色在下一次请求生效，不必把旧令牌列入黑名单。
5. `typ = wecom` 的玩家令牌仍走原策略，不读 `users`。

### 获取菜单

`POST /api/v1/permission` 无请求体。从 JWT 认出用户后：

- 超级管理员：按菜单目录返回两棵完整树。
- 普通角色：用 `role_menus` 过滤子菜单，再挂到父级。没有子菜单的父级省略。
- 没有角色：返回 `{ "menus": [] }`，仍然是 200。登录本身允许成功（Q8）。

响应示例：

```json
{
  "menus": [
    {
      "key": "club-management",
      "title": "俱乐部管理",
      "children": [
        { "key": "clubs", "title": "创建俱乐部", "path": "/clubs" }
      ]
    }
  ]
}
```

不返回俱乐部 id，也不返回 `accounts` 这类键以外的权限码。

### 账号

创建：邮箱转小写、密码至少 8 位、名称可空、角色必填、默认启用。角色必须存在，且不是超级管理员角色。邮箱冲突 409。

修改：密码字段省略或空字符串表示不改密码。不能把任何人改成超级管理员角色，不能修改超级管理员账号的角色、停用状态。不能停用自己。启用一个 `roleId` 为空的历史账号时，请求里必须带上角色，否则 400。

删除：不能删自己，不能删超级管理员。删除账号不删除他创建的俱乐部。

列表返回 id、邮箱、名称、是否停用、角色 id 和角色名称，不返回密码哈希。查询参数 `email` 可选，按邮箱包含关系过滤。

### 角色

创建和修改：名称唯一，冲突 409。`menuKeys` 只能是子菜单键。`clubIds` 去重。

普通操作者提交的 `clubIds` 必须都在他自己的可见俱乐部里，否则 400。保存时只替换他能看见的那部分绑定，他看不见的原绑定保留。超级管理员按请求全量替换 `role_clubs`。

超级管理员角色不能改名称、菜单和俱乐部绑定，不能删除。

删除普通角色时，若仍有 `users.roleId` 指向它，返回 409，不级联改账号。

### 俱乐部可见范围

`access` 对当前用户给出可见俱乐部 id：

- 超级管理员：不限制。
- 其他：`role_clubs` 中该角色的 `clubId`。没有角色时为空。

以下位置改为使用这份 id，不再使用 `userId` 相等：

| 位置 | 规则 |
|---|---|
| 俱乐部列表、修改、删除 | 不在可见范围内则列表不含，单条 404 |
| 人员列表、新增、编辑、删除、解除绑定、导入 | 俱乐部必须可见。未指定俱乐部的人员列表只含可见俱乐部 |
| 活动列表、详情、结束、签到情况、再次发送、发布 | 该活动的全部 `activity_clubs` 都在可见范围内才可见。缺一个则整场 404。发布时每个 `clubIds` 都必须可见 |

活动仍把创建人写入 `activities.userId`，只是不再用它过滤。这样角色绑了俱乐部之后，能看到别人在这些俱乐部上发布的活动；解绑后，创建人自己也看不到。

新建俱乐部与写入 `role_clubs` 放在同一事务。创建者是超级管理员时也写入一行，其他角色不会因此看见。创建者是普通角色时，事务提交后列表即可看到。

俱乐部名称仍是同一创建人下唯一。两个创建人可以有同名俱乐部，超级管理员会同时看到两行。

## 接口

前缀 `/api/v1`。除登录外，下列接口都要管理端 JWT。账号与角色接口另外要求菜单键。没有该菜单返回 403。俱乐部类接口不靠菜单键判断数据，只靠可见俱乐部；页面进不去由前端负责。

### 权限

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/permission` | 见「获取菜单」。无正文 |

未带 JWT、令牌失效、用户已停用：401。

### 账号

菜单键 `accounts`。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/accounts` | 列表。可选查询 `email` |
| POST | `/accounts` | 创建 |
| PATCH | `/accounts/:id` | 修改名称、角色、停用状态、密码 |
| DELETE | `/accounts/:id` | 删除 |

`POST /accounts` 正文：

| 字段 | 规则 |
|---|---|
| email | 必填，邮箱 |
| password | 必填，8 至 72 位 |
| name | 可空 |
| roleId | 必填，不能是超级管理员角色 |

`PATCH /accounts/:id` 字段都可选。`password` 为空则不改。`disabled` 为布尔。

### 角色

菜单键 `roles`。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/roles` | 列表。每项含名称、是否超级管理员、菜单键、已绑俱乐部 id，以及菜单数量和俱乐部数量 |
| POST | `/roles` | 创建 |
| PATCH | `/roles/:id` | 修改 |
| DELETE | `/roles/:id` | 删除 |

正文：

| 字段 | 规则 |
|---|---|
| name | 必填 |
| menuKeys | 字符串数组，可为空 |
| clubIds | uuid 数组，可为空 |

账号表单需要角色下拉时调用 `GET /roles`。因此有账号管理、没有角色管理的人，不能靠这个列表选角色。创建账号页同时需要两个菜单时才能选角色并保存。只有 `accounts`、没有 `roles` 时，`GET /roles` 为 403。

为避免账号管理被角色管理卡住，`GET /roles` 在持有 `accounts` 或 `roles` 时都允许。`POST`、`PATCH`、`DELETE` 仍只允许 `roles`。持有 `accounts` 的列表结果里去掉超级管理员角色，避免它出现在新建账号的下拉里。持有 `roles` 的超级管理员可以看到该角色，但 `PATCH` 和 `DELETE` 仍拒绝。

### 错误

| 情况 | 结果 |
|---|---|
| 邮箱或密码不正确、账号停用、JWT 失效 | 401 |
| 没有账号管理或角色管理菜单却调用对应写接口 | 403 |
| 俱乐部、人员、活动不在可见范围 | 404 |
| 菜单键非法、启用历史账号却没给角色、密码短于 8 位 | 400 |
| 邮箱重复、角色重名 | 409 |
| 删除自己、删除或停用超级管理员、删除仍有账号的角色、修改超级管理员角色 | 409 |

`POST /auth/register` 去掉。调用时按未注册路由处理。

## 前端

登录成功后立刻 `POST /permission`，把 `menus` 放在现有登录状态旁，不写入 JWT 所在的 `localStorage` 键。刷新页面时，`AppShell` 挂载后重新请求一次。退出时清掉。

侧栏按返回的树渲染，不再写死「俱乐部管理」四项。窄屏同样只渲染返回的子菜单。

路由增加菜单键。进入后台子路由时，若权限尚未返回则等待这一次请求。目标键不在返回的子菜单里，则进入返回结果中的第一个路径。结果为空时留在壳内，主区域说明当前没有可用菜单，不跳到 `/clubs`。

| 路由 | 菜单键 | 界面 |
|---|---|---|
| `/accounts` | `accounts` | 表格：邮箱、名称、角色、状态。可新建、编辑、停用或启用、删除。编辑时密码可留空 |
| `/roles` | `roles` | 表格：名称、菜单数量、俱乐部数量。编辑时用固定目录勾选菜单，用当前用户可见的俱乐部勾选绑定 |
| `/login` | 无 | 去掉注册链接 |
| `/register` | 无 | 删除该页。地址不再注册账号 |

直接输入 `/accounts` 而返回菜单里没有该项时，不挂载账号页。

玩家路由 `/a/:id` 仍是公开页，不请求 `/permission`。

## 技术选型与备选

| 决定 | 原因 | 不采用 |
|---|---|---|
| 菜单键放在共享类型里 | 目录固定，接口和路由必须用同一套键 | 把菜单做成可增删的表。梳理明确目录本身不可配置 |
| 菜单不写入 JWT | 改角色后下次请求即可生效，符合 Q7 | 登录响应里带菜单并缓存到令牌过期。停用和改权限都会滞后 |
| 停用在 JWT 校验时再查库 | 停用后下一次接口即失效，不必做令牌黑名单 | 只在登录时检查。已发出的 7 天令牌会继续可用 |
| `role_menus`、`role_clubs` 分表 | 俱乐部绑定会随新建俱乐部增加，用关联表才能做外键和级联 | 在 `roles` 上存 id 数组。少一张表，但俱乐部删除时清不干净 |
| 超级管理员用 `isSuper` | 可见全部俱乐部是规则，不是把所有俱乐部插入绑定表。新建俱乐部也不必给超级管理员补绑定才看得见 | 启动时把全部俱乐部绑到超级管理员角色。俱乐部一多就会漏，也和「不依赖绑定」相反 |
| 活动要求全部已选俱乐部可见 | 签到情况会列出这些俱乐部的人员。只绑到其中一个就放开，会看到未授权俱乐部的玩家 | 按 `activities.userId` 继续隔离。角色绑了俱乐部仍看不到别人发布的活动，和梳理不符 |
| 普通角色保存俱乐部时只替换可见部分 | 操作者看不到的绑定如果被整表覆盖，会在不知情下被清空 | 要求每次提交全量 id。普通角色拿不到自己看不见的俱乐部 id |
| 迁移一次性停用旧账号 | 再次启用必须能保留 | 每次启动把非超级管理员设为停用 |

## 风险与对策

| 风险 | 对策 |
|---|---|
| 未配置超级管理员环境变量 | 启动记错误。旧账号已在迁移中停用，注册接口已关闭，避免无人值守时冒出管理员 |
| 每次启动误伤已启用账号 | 停用只写在迁移里。启动只upsert超级管理员本人 |
| 有角色管理的人给自己的角色勾上更多菜单 | 梳理允许持有该菜单的人维护角色。限制停留在不能碰到超级管理员角色、不能分配自己看不见的俱乐部 |
| 只有页面拦截时，知道地址的人仍能调用自己可见俱乐部的接口 | 与「数据范围按俱乐部、`/permission` 只给菜单」一致。账号和角色的写接口额外校验菜单键 |
| 一场活动跨了未授权俱乐部 | 整场 404，签到人员列表不会混出别的俱乐部 |
| 历史账号 `roleId` 为空却被启用 | 启用请求必须同时带角色 |
| 同名俱乐部在超级管理员列表里分不清 | 保留创建人字段供列表展示俱乐部时带上创建人邮箱。本需求不改名称唯一规则 |
| 删除俱乐部后角色上还留着绑定 | `role_clubs.clubId` 随俱乐部删除而级联删除 |

## 与梳理版的追溯

| 用例 / 验收 | 设计落点 |
|---|---|
| UC-01、验收 1 | 启动按环境变量保证超级管理员；`isSuper` 返回全部菜单、查询俱乐部不读 `role_clubs` |
| UC-02、验收 3 | `POST /api/v1/permission`；JWT 失败 401；响应只有菜单树 |
| UC-03、验收 4 | `/accounts`；一账号一个 `roleId`；密码 8 至 72 位；邮箱唯一 |
| UC-04、UC-10、验收 5 | `users.disabled`；登录和 JWT 校验都拒绝停用；`PATCH` 可改回启用，密码可空 |
| UC-05 | `/roles` 与 `role_menus`、`role_clubs` |
| UC-06、验收 6 | `access` 的可见俱乐部用于俱乐部、人员、导入、活动 |
| UC-07、验收 7、8 | 创建俱乐部的同一事务写 `role_clubs`。其他角色没有这行就 404 |
| UC-08 | 前端按菜单键拦截路由。账号和角色写接口再校验菜单键 |
| UC-09、验收 2 | 迁移把已有用户 `disabled = true`。启动不会反复执行 |
| 验收 9 | 删除自己、删除或改超级管理员、删除仍被使用的角色返回 409 |
| 验收 10 | 移除注册接口和注册页。玩家令牌不读角色 |
| Q1 | `SUPER_ADMIN_EMAIL`、`SUPER_ADMIN_PASSWORD` |
| Q2 | 不能对超级管理员账号和角色做删除、停用、改角色；下拉不提供该角色 |
| Q3 | 普通角色保存 `clubIds` 时校验可见范围，并保留看不见的原绑定 |
| Q4 | `roles.name` 唯一 |
| Q5 | 删除前统计 `users.roleId`，有人则 409 |
| Q6 | 删除或停用当前用户返回 409 |
| Q7 | 菜单和角色不进 JWT，下次请求读库 |
| Q8 | 无菜单时 `/permission` 返回空数组，前端不进入业务页 |
