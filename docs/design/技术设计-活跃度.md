# 技术设计 · 活跃度

依据 [需求梳理版](../detail/需求-活跃度-梳理版.md)。身份已定为方案 D，未对照的人按方案 B 认领。本版只定方案，不改代码。

## 目标与约束

活动签到改到「活动管理」下，由管理员勾选参加人员。人员列表提供「查询活跃度」。小忧只读回答活动，不再回答企业微信绑定。

沿用 Vue 3、Element Plus、NestJS、PostgreSQL、Prisma 和小忧现有的意图加场景文案。不新增队列或缓存。

| 已有能力 | 本需求中的用法 |
|---|---|
| `MENU_CATALOG` 与 `activities` 菜单键 | 把「活动签到」换父菜单，键和路径不变，已有角色授权继续有效 |
| `activities`、`activity_clubs` | 继续存活动。发布只写标题、俱乐部、开始时间 |
| `members` 导入 | 同名原地更新。需要对照时先不提交，确认后再改名或删除 |
| 小忧 `plan.ts`、意图技能、场景技能 | 去掉绑定；增加四个只读活动工具 |
| `activity_check_ins`、企微相关表 | 列保留。新签到不读、不写这些表 |

约束：

- `activities.wecomTeamId` 改为可空，列不删。发布不再要求企业微信已配置，也不写接收人和通知。
- 新参加记录与旧的 `activity_check_ins` 分开，不迁移旧签到。
- 俱乐部内玩家名称仍然唯一。对照只允许「本次将删除的旧行」对「本次将新建的新名称」，一对一。
- 活动可见范围继续用 `AccessService.activityWhere`：非超管必须能看见该活动的每一个俱乐部。
- 小忧不能发布、修改、删除、结束或代为勾选。

## 总体架构

```text
管理员浏览器
  活动管理 / 活动签到
  俱乐部管理 / 人员列表、导入人员
        │  JWT /api/v1
        ▼
NestJS
  activities    发布、修改、删除、结束、勾选签到
  members       导入对照、改名同步、删除时解开参加记录、活跃度查询
  xiaoyou       四个只读活动工具；人员回答不再含绑定
        │
        ▼
PostgreSQL
  activities, activity_clubs
  activity_attendances（新建）
  members
```

玩家页 `/a/:id`、`/api/v1/player/activities`、`/api/v1/wecom` 和每分钟提醒不再挂到应用上。`wecom_teams`、`wecom_bindings`、`activity_recipients`、`activity_notifications`、`activity_check_ins` 留在库里。

## 模块职责

| 模块 | 职责 |
|---|---|
| `activities` | 发布、修改、删除、结束；按当前俱乐部名单勾选并整表保存参加记录 |
| `members` | 导入前判断要不要对照；按对照改名或删除；创建同名人员时认领空挂记录；人员列表改名时改快照 |
| `xiaoyou` | 识别活动问法，按可见范围回答列表、单场、出席和某人活跃度 |
| Web 活动页 | 父菜单、三项发布、改删、签到弹窗。去掉提醒、接收人、重发和签到情况页 |
| Web 人员 | 去掉绑定列和解除绑定；增加活跃度弹窗；导入增加对照弹窗 |
| `shared-types` | `MENU_CATALOG` 增加父菜单「活动管理」 |

`ActivitiesModule` 不再导入 `WecomModule`，不再注册 `PlayerController` 和 `ReminderService`。没有其他定时任务时，`AppModule` 去掉 `ScheduleModule`。

## 关键流程

### 发布、修改、结束、删除

发布只校验标题、至少一个可见俱乐部、开始时间。`remindAt`、接收人留空。`wecomTeamId` 写空。状态仍是 `PUBLISHED`。不调用企业微信。

修改可改标题、俱乐部集合、开始时间。已结束的活动也能改。更换俱乐部不删除已有参加记录。

结束只把状态改为 `ENDED` 并写下 `endedAt`。不拒绝之后的签到和修改。

删除活动时，数据库级联删除该活动的参加记录。

### 勾选签到和迟到

`GET` 返回该活动当前所选俱乐部的在册人员，以及每人是否已签到、是否迟到。已结束同样返回。

`PUT` 提交 `{ memberId, late }` 列表，这些人都必须属于当前所选俱乐部。`late` 为真表示迟到。保存时：

- 名单里有、但还没有记录的，插入一条，并写下 `late`。
- 已有记录的，只更新 `late`。
- 当前名单里去掉签到的，删除指向该人的记录，迟到一并消失。
- 不在当前名单里的旧记录不动。其中包括已经不在这些俱乐部、或人员 id 已清空的记录。

没有出现在提交列表里的当前人员就是未签到。`late` 省略或为假，就是不迟到。提交了迟到但没把这个人算进签到时，按已签到且迟到保存。界面上勾迟到会同时勾上签到，取消签到会同时取消迟到。

同一活动、同一人员多次保存只有一条。弹窗不展示签到时刻。

### 导入对照（方案 D）

确认导入时仍先按现有规则匹配：同俱乐部名称对得上的原地更新；对不上的是待新建；当前有、名单里没有的是待删除。

待删除的人里，只要还有参加记录指向他，就称为「有历史的缺失」。本次又存在待新建名称时，接口不写库，返回 `NEED_RENAME`：

| 字段 | 含义 |
|---|---|
| `missing` | 有历史的缺失：人员 id、玩家名称、参加场数 |
| `arriving` | 本次待新建的玩家名称 |

导入页留在核对页，弹出对照。每一行可选一个待新建名称，也可以不选。一个旧行只能对一个新名称，一个新名称只能被对一次。

再次提交时带上 `renames: [{ memberId, playerName }]`，空数组表示全部不对。服务端在原有事务里：

1. 对照项：用待新建行的字段更新旧行，人员 id 不变，并把该人所有参加记录的名称快照改成新名称。该名称不再新建，该行不再删除。
2. 其余待删除：删除人员。参加记录保留，`memberId` 置空，名称快照仍是旧名称。
3. 其余待新建：新建人员后，按「俱乐部 + 玩家名称」认领 `memberId` 为空的记录。
4. 同名更新：与现在一样，id 不变。

没有「有历史的缺失」，或没有待新建名称时，不返回 `NEED_RENAME`，直接按上面的删除和认领执行。没有历史的缺失人员仍然直接删除，不进入对照。

人员列表里改名走同一行更新，并同步该 `memberId` 下的名称快照。手工新增人员后做一次同名认领。删除人员不删除参加记录。

认领时，若该活动已经有指向这个新人员 id 的记录，则留下已挂上的那条，删掉重复的空挂记录。

### 查询活跃度

已签到：参加记录的 `memberId` 等于这一行，且活动对当前用户可见。记录上的 `late` 为真时，这场同时是迟到。

未签到：活动对当前用户可见，活动俱乐部包含该人所在俱乐部，且没有指向这个 `memberId` 的记录。

`memberId` 为空的记录不出现在任何人的已签到里，直到被认领。认领时保留原来的 `late`。其他俱乐部的活动两边都不出现。已结束的活动照样出现。

历史详情是只读展示。每场活动显示绿色的「已签到」或红色的「未签到」；`late` 为真时再显示红色的「迟到」。不返回、也不展示「未迟到」。绿字只用于「已签到」，红字只用于「未签到」和「迟到」。活动标题和时间不着色。小忧回答同一套事实，不带颜色。

### 小忧

问法先于人员资料匹配，避免「张三参加了哪些活动」被收成查等级。绑定、企业微信不再映射到人员字段；这类问法走帮助，说明不再提供绑定状态。全部资料不包含绑定。

活动标题的匹配和俱乐部一样：唯一全称直接答，唯一包含先确认，多个则选择。选人和现有人员选择共用。

| 工具 | 菜单 | 结果 |
|---|---|---|
| `list_activities` | `activities` | 可见活动的标题、俱乐部、开始时间、状态。可按俱乐部、已发布或已结束过滤 |
| `get_activity` | `activities` | 一场的标题、俱乐部、开始时间、状态、已签到人数、未签到人数、迟到人数 |
| `activity_roster` | `activities` | 已签到名单、未签到名单，或只要一边，并带人数。迟到的人在已签到名单中标明，并给出迟到人数。未签到只含当前所选俱乐部的在册人员 |
| `member_activities` | `members` | 与活跃度弹窗同一套已签到、未签到、迟到，并带这三类场数 |

没有 `activities` 菜单时，前三个工具用现有无菜单场景。`member_activities` 与人员查询一样，要求 `members` 菜单。名单单边超过 30 人时，先说人数，只列前 30 个名称，并说明剩余人数。

帮助文案去掉绑定，补上查看活动、查看一场出席、查看某人参加过和没参加的活动。

## 数据模型

新建 `activity_attendances`：

| 列 | 规则 |
|---|---|
| `id` | 主键 |
| `activityId` | 必填，活动删除时级联删除 |
| `memberId` | 可空。人员删除时置空，不级联删除本行 |
| `clubId` | 必填，取勾选时该人员所在俱乐部。俱乐部删除仍先被「已被活动使用」拦住 |
| `playerName` | 必填，勾选或改名时的名称快照 |
| `late` | 布尔，默认假。真表示迟到。没有这一行就是未签到，不另存「未迟到」 |
| `createdAt` | 写入时间，界面不展示 |

唯一约束：

- 同一活动、同一个非空 `memberId` 只有一条。
- 同一活动、同一俱乐部、同一玩家名称只有一条。

`activities.wecomTeamId` 改为可空，外键仍指向 `wecom_teams`。不删列，不删企微各表，不把 `activity_check_ins` 抄进新表。

## 接口

都在现有 `/api/v1` 下，沿用 JWT。俱乐部和活动的可见性沿用 `AccessService`。

| 方法 | 路径 | 变化 |
|---|---|---|
| `POST /activities` | 入参只保留 `title`、`clubIds`、`startsAt`。不再要求提醒和接收人，不返回发送结果 |
| `PATCH /activities/:id` | 新增。入参与发布相同，整体替换俱乐部关联 |
| `DELETE /activities/:id` | 新增。删除活动及其参加记录 |
| `GET /activities/:id/attendance` | 新增。当前俱乐部人员：`id`、`playerName`、`clubName`、`attended`、`late` |
| `PUT /activities/:id/attendance` | 新增。入参 `marks: [{ memberId, late }]`。按上一节规则增删和更新迟到 |
| `POST /activities/:id/end` | 保留。结束后仍允许修改、删除和签到 |
| `GET /members/:id/activities` | 新增。`attended`、`missed`。已签到项含 `late`。每项还有 `id`、`title`、`clubs`、`startsAt`、`status`。界面把「已签到」渲染为绿字，「未签到」和「迟到」渲染为红字 |
| `POST /clubs/:clubId/imports` | 增加可选 `renames`。需要对照且没带该字段时返回 409，体为 `{ code: "NEED_RENAME", missing, arriving }`，不写人员、不留已上传图片 |
| `DELETE /members/:id/wecom-binding` | 卸下 |
| `POST /activities/:id/notifications` | 卸下 |
| `GET /activities/:id/check-ins` | 卸下，签到改走 `attendance` |
| `/player/activities/*`、`/wecom/*` | 卸下 |

`GET /activities` 和 `GET /activities/:id` 保留。返回里不再带通知状态。

## 界面

`MENU_CATALOG` 增加分组 `activity-management` / 「活动管理」，子项仍是 `activities` / 「活动签到」/ `/activities`。从「俱乐部管理」拿走该项。空分组不显示，现有 `menusForKeys` 已是这样。

活动列表操作：签到、编辑、删除、结束。去掉签到情况、重发卡片、重发提醒、通知列。编辑弹窗只有标题、俱乐部、开始时间。

人员列表去掉「是否绑定通知」和解除绑定，操作列增加「查询活跃度」。导出表去掉绑定列。排序字段去掉 `notifyBound`。

签到弹窗用两列勾选。查询活跃度弹窗在每场活动上显示绿字「已签到」或红字「未签到」，迟到另起一个红字。绿色和红色都用固定颜色，不跟随主题改色。

导入核对页在收到 `NEED_RENAME` 时打开对照弹窗，确认后带 `renames` 重新提交原来的图片和行。

路由去掉 `/a/:id` 和 `/activities/:id`。`AppShell` 里活动路径的高亮改为新菜单路径 `/activities`，逻辑不变。

## 技术选型与备选

| 决定 | 不采用的做法 |
|---|---|
| 新表 `activity_attendances`，人员外键 `ON DELETE SET NULL` | 继续写 `activity_check_ins`。那张表带企微用户，并且人员删除会级联删掉签到 |
| 导入用 409 暂停，前端原样重试 | 先把人删掉再让管理员补对照。那样 id 已经变了，方案 D 无法只改名称 |
| 小忧沿用本地规则优先、模型意图补充 | 另做一套对话服务 |
| 企微模块从应用启动链卸下，表保留 | 继续在发布时调用发卡片。也不同步删库，避免动到「字段先保留」 |

## 风险与对策

| 风险 | 对策 |
|---|---|
| 管理员漏对照，改名被当成新人 | 有历史的缺失一定先弹出对照。漏选则记录留在旧名称上，同名回来才能认领，不会进新名字的活跃度 |
| 一张导入里旧名和新名都在 | 旧名能匹配上，不会进入缺失列表，因此不会自动合并。这是两名在册人员 |
| 空挂记录与新行在同一活动上撞唯一约束 | 认领时保留已指向新人员的那条，删掉空挂的重复行 |
| 更换活动俱乐部后，旧勾选不在弹窗里，无法取消 | 与梳理版一致，这些记录保留，活跃度仍算已参加 |
| 旧签到页或玩家链接仍被打开 | 路由和接口卸下，不再读写 `activity_check_ins` |
| `wecomTeamId` 原为必填，旧行都有值 | 迁移只放宽为可空。旧行保留原值，新发布写空 |
