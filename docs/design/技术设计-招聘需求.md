# 技术设计 · 招聘需求

依据 [需求梳理版](../detail/需求-招聘需求-梳理版.md) 的暂定结论（Q1–Q13）。本版只定方案，不改代码。

## 目标与约束

增加一张公开申请页，以及后台「招聘管理 / 申请列表」。申请单独存表。同意、不同意、已读都不读写 `members`。

沿用现有技术栈，不新增依赖：

| 已有能力 | 本需求中的用法 |
|---|---|
| Vue 3 + Element Plus + Vue Router | `/apply` 独立页；`/applications` 管理页 |
| NestJS + JWT + `MenuGuard` | 管理接口要登录，并且要有菜单 `applications` |
| PostgreSQL + Prisma | 新增 `applications` |
| `AccessService.clubWhere` | 管理端按角色可见俱乐部过滤 |
| `MENU_CATALOG` | 增加大菜单，角色页的勾选列表随之出现 |

约束：

- 「工会」就是现有 `clubs`。公开下拉只给出 `id` 和 `name`。
- 现有 `GET /api/v1/clubs` 继续要 JWT，并按角色过滤。申请页另开公开接口，避免把管理列表放开。
- 公开接口不挂 `JwtAuthGuard`。现有前端在任意 401 时会清令牌并跳到 `/login`，申请页不能走到这条分支。
- 删除俱乐部的现有规则不变：有人员或被活动引用时仍拒绝删除。申请不能成为删除俱乐部的新障碍。
- 超级管理员的菜单在登录时按 `MENU_KEYS` 展开，不必给超级角色补 `role_menus` 数据。其他角色要在角色管理里勾选「申请列表」后才看得到。

## 总体架构

```text
申请人浏览器                         管理员浏览器
  /apply（无 AppShell）                 /applications（AppShell）
        │                                      │
        │  无守卫                              │  JWT + MenuGuard
        ▼                                      ▼
NestJS  applications
  GET  /apply/clubs
  POST /apply
  GET  /applications
  GET  /applications/:id     打开即写 readAt
  PATCH /applications/:id    只改 decision
        │
        ▼
PostgreSQL
  applications ──► clubs（可空，删除俱乐部时置空）
  members 不参与
```

新模块注册到 `AppModule`。`clubs`、`members` 的控制器和服务不改行为。

## 模块职责

| 模块 | 职责 |
|---|---|
| `packages/shared-types` 的 `MENU_CATALOG` | 在「俱乐部管理」和「系统管理」之间增加「招聘管理 / 申请列表」 |
| `applications` | 公开俱乐部名单、提交申请、管理端列表、详情已读、同意或不同意 |
| `access` | 复用 `clubWhere`，判断一条申请是否落在当前角色的俱乐部范围内 |
| Web 路由 | `/apply` 标为 `public`，放在 `AppShell` 之外；`/applications` 挂在壳内，`meta.menu = applications` |
| Web `api/client.ts` | 增加五个调用。继续用现有 `api` 实例 |

侧栏图标：招聘管理不是 `system`，会沿用现有建筑图标，不新增图标。

## 关键流程

### 打开申请页

1. 路由 `/apply` 的 `meta.public` 为真，未登录也能进入，不渲染侧栏和小忧面板。
2. 页面请求 `GET /apply/clubs`。
3. 下拉展示俱乐部名称，值为俱乐部 id。列表为空时无法选择，提交停在前端校验。

### 提交

1. 前端五项都有值才请求。服务端仍全部校验，不信任前端。
2. 文本去掉首尾空白。空白视为未填。游戏名称、uid 最长 64，理由最长 500。非凡评分为 0 到 2147483647 的整数。
3. 用俱乐部 id 查 `clubs`。不存在则 400，文案「所选工会不存在」，不插入申请。
4. 插入一行：处理状态 `PENDING`，`readAt` 为空，并抄一份当时的俱乐部名称。
5. 成功响应 `{ ok: true }`。页面清空表单并显示成功。失败显示接口返回的原因，保留已填内容。
6. 不按 uid 或游戏名称查重。连续提交得到多行。

### 列表与已读

1. `GET /applications?read=unread` 或 `read=read`。缺省或其他值返回 400。页面默认请求 `unread`。
2. 超级管理员看全部。其他账号只看 `clubId` 落在 `AccessService.clubWhere` 内的行。
3. 未读是 `readAt` 为空，已读是 `readAt` 有值。按 `createdAt` 降序返回当前范围内的全部行，本版不做分页。
4. 列表接口不写 `readAt`。
5. `GET /applications/:id` 先确认这条在可见范围内，否则 404。若 `readAt` 为空，写成当前时间。再次打开不改这个时间。
6. 详情对话框拿到响应后，列表按当前档重新查询，该行从「未读」消失、出现在「已读」。

### 同意与不同意

1. `PATCH /applications/:id`，正文只接受 `APPROVED` 或 `REJECTED`。
2. 同样先做可见范围检查。不可见为 404。
3. 只更新 `decision`。不改 `readAt`，不调用人员服务，不插入 `members`。
4. `PENDING` 不能经这个接口写回。待处理只能被改成同意或不同意，后两者可以互换。
5. 俱乐部后来被改名时，列表和详情显示俱乐部当前名称。俱乐部已被删除时，显示提交时抄下的名称；`clubId` 为空。这类行只有超级管理员能在列表和详情里看到。

## 数据模型

新增枚举和一张表。`Club` 增加反向关系。`onDelete: SetNull`，这样现有删除俱乐部逻辑不用先数申请行。

### ApplicationDecision

| 值 | 界面 |
|---|---|
| `PENDING` | 待处理 |
| `APPROVED` | 同意 |
| `REJECTED` | 不同意 |

### applications

| 字段 | 类型 | 规则 |
|---|---|---|
| id | uuid | 主键 |
| clubId | uuid，可空 | 外键指向 `clubs.id`，删除俱乐部时置空 |
| clubName | string | 提交时的俱乐部名称，俱乐部删除后仍用于展示 |
| gameName | string | 游戏名称，不与 `members.playerName` 关联 |
| score | int | 非凡评分 |
| uid | string | 原文 |
| reason | string | 选择无忧的理由 |
| decision | 枚举 | 默认 `PENDING` |
| readAt | 时间，可空 | 空为未读；首次打开详情时写入 |
| createdAt / updatedAt | 时间 | 提交时间用 `createdAt` |

索引：`(clubId, readAt, createdAt)`。

不建与 `members` 的外键，也不按游戏名称、uid 建唯一约束。

## 接口

前缀 `/api/v1`。

### 公开

不使用 `JwtAuthGuard` 和 `MenuGuard`。请求里即使带了过期令牌也不校验，成功和失败都不返回 401。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/apply/clubs` | `[{ id, name }]`，按名称排序。无俱乐部时为 `[]` |
| POST | `/apply` | 提交。成功 `{ ok: true }` |

`POST /apply` 正文：

| 字段 | 规则 |
|---|---|
| gameName | 非空字符串，最长 64 |
| score | 整数，0 到 2147483647 |
| uid | 非空字符串，最长 64 |
| clubId | UUID v4，且俱乐部仍存在 |
| reason | 非空字符串，最长 500 |

校验失败 400，消息用现有 `ValidationPipe` 的首条文案，例如「请填写游戏名称」「非凡评分必须是整数」「所选工会不存在」。多出来的字段拒绝。

### 管理

控制器使用 `JwtAuthGuard` 和 `MenuGuard`，类上 `@RequireMenu('applications')`。无令牌 401。有令牌但无此菜单 403，文案沿用「没有权限」。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/applications` | 查询参数 `read=unread` 或 `read=read` |
| GET | `/applications/:id` | 详情，并把未读写成已读 |
| PATCH | `/applications/:id` | `{ decision: "APPROVED" \| "REJECTED" }` |

列表每一行：`id`、`gameName`、`score`、`uid`、`clubName`、`createdAt`、`read`、`decision`。不含理由。

详情在列表字段上增加 `reason`。`read` 在本次响应里为 `true`。

不可见或不存在的 id 都是 404，文案「申请不存在」，避免泄露其他俱乐部的申请。

## 前端

| 页面 | 路由 | 界面 |
|---|---|---|
| 申请表 | `/apply` | 居中卡片。标题下固定文案「无忧大家庭欢迎你的加入~」。`el-form`：游戏名称、非凡评分、uid、工会 `el-select`、理由多行文本。主按钮提交。结果用 `el-alert` |
| 申请列表 | `/applications` | `el-radio-group` 或分段切换未读 / 已读，默认未读。`el-table` 展示列表字段。处理状态列把枚举显示成待处理、同意、不同意。操作：详情、同意、不同意 |

详情用 `el-dialog`。打开时请求详情接口。对话框内展示五项、提交时间、已读、处理状态，以及同意、不同意按钮。关闭后刷新当前档列表。

列表上的同意、不同意直接调用 `PATCH`，不请求详情，因此未读行可以在不打开详情时被标记，并保持未读。

失败文案走现有 `errorMessage`。申请页的失败只显示在卡片内，不跳转。

角色管理已按 `MENU_CATALOG` 渲染勾选，新菜单会出现在「招聘管理」下，不用改角色页结构。

## 技术选型与备选

| 决定 | 原因 | 不采用 |
|---|---|---|
| 新模块 `applications`，公开路径与管理路径分开 | 公开接口不能挂全局登录守卫；也不改 `GET /clubs` 的权限 | 给 `GET /clubs` 增加匿名模式。那会和管理列表的过滤缠在一起 |
| `readAt` 空值表示未读 | 满足「打开详情才已读」，并保留首次打开时间 | 布尔 `read`。布尔看不出是谁在何时点开，而时间字段不增加接口复杂度 |
| 打开详情的 GET 顺带写入 `readAt` | 和「点击详情」是同一次操作，列表接口保持只读 | 单独 `POST /read`。多一次请求，页面漏调就会一直未读 |
| 抄俱乐部名称，外键可空且 `SetNull` | 删除俱乐部的现有判断不用改；删掉后列表仍能显示当时的工会 | 外键限制删除。有申请的空俱乐部会删不掉，改变现有俱乐部规则 |
| 管理接口使用 `MenuGuard` | 梳理要求没有菜单就不能调接口。俱乐部和人员接口目前只校验登录，本需求更严 | 只在前端路由拦截。直接调 API 仍能读写申请 |
| 本版不分页 | 梳理把分页放在 Could | 先做分页。当前没有数量上限要求 |

## 风险与对策

| 风险 | 对策 |
|---|---|
| 公开接口暴露全部俱乐部名称 | 按 Q2 接受。响应只有 id 和名称，没有会长和人员 |
| 无验证码，可被重复刷申请 | 按 Q13 和 Won't 接受。每条独立保存，不自动入库 |
| 申请人浏览器里留有过期令牌 | 公开接口不校验令牌，也不返回 401，拦截器不会把人带到登录页 |
| 俱乐部改名或删除后，工会对不上 | 未删除时读当前名称；已删除时读 `clubName`。非超级管理员看不到已删除俱乐部的申请 |
| 列表误调详情接口，整页变成已读 | 表格数据只用列表接口。详情只在点击「详情」时请求 |
| 同意被误接成人员入库 | `PATCH` 只更新 `applications.decision`，模块不注入人员服务 |
| 已有非超级角色看不到新菜单 | 预期行为。超级管理员立刻可见；其他角色在角色管理勾选「申请列表」，并仍受俱乐部范围限制 |
