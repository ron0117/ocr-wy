# 技术设计 · 签到表 2.0

依据 [需求梳理版](../detail/需求-签到表2.0-梳理版.md)。本版只定方案，不改代码。

## 目标与约束

在现网 **Vue 3 + Element Plus + NestJS + PostgreSQL + Prisma** 上，将活动参加方式从「管理员勾选 `activity_attendances` + `memberId`」改为 **公开 `/a/:id` 表单报名**，数据写入 **新表**；后台增加 **活动查看**（查改删、出席三态、导出）。**不写 `members`、不写 `memberId`、不用企微通知**。签到表 1.0 作废；小忧不改造。

| 已有能力 | 本需求中的用法 |
|---|---|
| `activities` / `activity_clubs` | 发布字段不变；公开页俱乐部下拉来自关联表 |
| `ActivityAttendance` | **停止读写**；历史只读（活跃度仍可读旧数据） |
| `ApplyController` 模式 | 公开接口无 JWT，挂在独立 Controller |
| `export-members.ts` | 活动查看导出对齐同一 ExcelJS 版式 |
| `WEB_ORIGIN` | 拼公开链接 `{WEB_ORIGIN}/a/{activityId}` |

约束：

- 公开报名 **无 token**；仅 `PUBLISHED` 可成功提交；`ENDED` 可打开页但提交拒绝。
- 防刷：**每活动 + 每 IP** 最多 **5 次成功创建**；重复 `(activityId, clubId, playerName)` 拒绝。
- 活动查看：**任意已登录用户** 可看任意活动的全部报名（不做 `AccessService` 过滤）；菜单 **全员可见**，角色里不必单独勾选。
- 活动发布/改删：仍走现有 **俱乐部可见性**（`activities` 模块不变权限模型）。
- 导入人员：**删除**与 `activity_attendances` 相关的对照、认领、改名同步逻辑。

## 总体架构

```text
玩家浏览器 / 嵌入 iframe
  /a/:activityId（无 AppShell）
        │  GET/POST /api/v1/public/activities/:id
        ▼
NestJS
  public-activities（公开读活动、提交报名）
  activity-registrations（后台 CRUD、列表、导出用数据）
  activities（发布、改删、结束；展示链接/二维码所需 id）
  members（导入/删改；去掉 attendance 联动）
        │
        ▼
PostgreSQL
  activities, activity_clubs（沿用）
  activity_registrations（新建）
  activity_attendances（只读遗留）

管理员浏览器
  /activities（链接+二维码；跳转查看）
  /activity-registrations?activityId=
        │  JWT；活动查看接口不校验 menuKey
        ▼
  同上 NestJS 模块
```

## 数据模型

### 新表 `activity_registrations`

Prisma 模型名建议 `ActivityRegistration`，表名 `activity_registrations`。

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | UUID PK | |
| `activityId` | UUID FK → `activities` | `onDelete: Cascade` |
| `clubId` | UUID FK → `clubs` | 须属于该活动的 `activity_clubs` |
| `playerName` | String | 非凡者名称，trim 后存 |
| `score` | Int | 1–999999 |
| `profession` | Enum 或 String | 见下 |
| `attendanceStatus` | Enum | `NORMAL` / `LATE` / `ABSENT`，默认 `NORMAL` |
| `submitIp` | String | 提交时客户端 IP（见「IP 获取」） |
| `createdAt` | DateTime | |
| `updatedAt` | DateTime | |

索引与约束：

- `@@unique([activityId, clubId, playerName])` — 对应「当前活动已报名」。
- `@@index([activityId, createdAt])` — 列表默认排序。
- `@@index([activityId, submitIp])` — IP 次数统计。

**职业枚举**（与梳理版一致，建议放 `packages/shared-types`）：

`AUDIENCE` | `SUN` | `FOOL` | `WARRIOR` | `APPRENTICE` | `DIVINATION`  
展示文案：观众、歌颂、窥秘、战士、学徒、占卜。

**出席状态枚举**：`RegistrationAttendanceStatus` → NORMAL / LATE / ABSENT；库内枚举，接口与前端用 code，列表展示中文。

### 旧表 `activity_attendances`

- 迁移 **不删表、不迁数据**。
- 移除 `activities` 的 `GET/PUT .../attendance` 及 `saveAttendance` 实现。
- `members` 导入/删除/改名 **不再** 读写该表（见「members 清理」）。
- `members.activities()`、小忧活动出席 **仍只查** `activity_attendances`（新报名不出现，符合梳理版）。

### `activities` 其它列

`remindAt`、`wecomTeamId`、接收人/通知/ check-in 等列保留，本功能不读写。

## 接口设计

前缀均为 `/api/v1`（与现网一致）。公开接口 **不加** `JwtAuthGuard`。

### 公开 · 活动与报名

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `public/activities/:id` | 返回 `{ id, title, startsAt, status, clubs: [{ id, name }] }`；活动不存在 404 |
| POST | `public/activities/:id/registrations` | Body 见下；成功 201 + 记录摘要 |

**POST Body**

```ts
{
  clubId: string;      // uuid
  playerName: string;
  score: number;       // 正整数，≤ 999999
  profession: ProfessionCode;
}
```

**校验顺序**（同一事务或等价原子逻辑）：

1. 活动存在且 `status === PUBLISHED`，否则 400（ENDED 文案如「活动已结束，无法报名」）。
2. `clubId` 属于该活动 `activity_clubs`。
3. `playerName` 非空（长度上限可与 members 一致，如 64）。
4. `score` 整数、1–999999。
5. `profession` 合法枚举。
6. 统计 `activity_registrations` 中 `activityId + submitIp` 行数 ≥ 5 → 400「您已报名多次，报名失败」。
7. 违反唯一约束 → 409 或 400「当前活动已报名」。

**IP 获取**：Nest 开启 `trust proxy`（若尚未）；优先 `X-Forwarded-For` 第一个合法 IP，否则 `req.ip`；存字符串。

失败 **不** 计入 IP 五次（仅 **成功 insert** 计数）。

### 后台 · 活动查看

控制器类级 `@UseGuards(JwtAuthGuard)`，**不使用** `MenuGuard`（任意登录用户可调）。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `activity-registrations/activities` | 全部活动 `{ id, title, startsAt, status, publishedAt }[]`，按 `publishedAt desc`（与「默认最新一场」一致） |
| GET | `activity-registrations` | Query：`activityId`（必填）、`clubId?`、`sortBy?`、`sortOrder?`；返回 `{ rows, activity, clubs }` |
| PATCH | `activity-registrations/:id` | 改 clubId/playerName/score/profession/attendanceStatus；遵守活动俱乐部与唯一约束 |
| DELETE | `activity-registrations/:id` | 删一条 |

**GET 列表 Query**

| 参数 | 说明 |
|---|---|
| `activityId` | 必填；缺省前端不应请求 |
| `clubId` | 可选，限定在该活动 clubs 内 |
| `sortBy` | `playerName` \| `clubName` \| `score` \| `profession` \| `attendanceStatus` \| `createdAt` |
| `sortOrder` | `asc` \| `desc`；默认 `createdAt desc` |

返回行字段：`id, playerName, clubId, clubName, score, profession, professionLabel, attendanceStatus, statusLabel, submitIp, createdAt, updatedAt`。

**活动发布侧**（现有 `activities`）：保持 `@UseGuards(JwtAuthGuard)` + 现有 `owned`/`activityWhere`；不在此模块暴露全量活动给无权限用户。

### 删除的接口

| 方法 | 路径 |
|---|---|
| GET | `activities/:id/attendance` |
| PUT | `activities/:id/attendance` |

## 前端设计

### 路由

| 路径 | 组件 | meta |
|---|---|---|
| `/a/:activityId` | `ActivitySignup.vue` | `{ public: true }` — 与 `/login`、`/apply` 相同，不走 AppShell、不校验 menu |
| `/activity-registrations` | `ActivityRegistrations.vue` | `{ menu: 'activity-registrations' }` |

`router.beforeEach` 扩展：

- `public: true` 照旧。
- 对 `menu: 'activity-registrations'`：**只要已登录即放行**，不检查 `auth.state.menus`（与梳理版「全员菜单」一致）。

### 菜单与权限

`MENU_CATALOG` 在「活动管理」下增加：

```ts
{ key: 'activity-registrations', title: '活动查看', path: '/activity-registrations' }
```

`PermissionController` 或 `menusForKeys` **后处理**：对每个已登录用户，若侧栏缺少 `activity-registrations`，则 **自动注入**（超管已有全量 `MENU_KEYS` 无需特殊处理）。

`Roles.vue` 仍从 `MENU_CATALOG` 渲染可分配项：可保留该键（勾不勾不影响，最终以注入为准），或在 catalog 标记 `assignable: false` 仅实现期择一，避免运营误解。**推荐**：角色编辑器 **不展示** `activity-registrations`（单独常量 `ALWAYS_VISIBLE_MENUS`），仅 permission 响应注入。

### 活动签到页 `Activities.vue`

- 移除签到弹窗及相关 API。
- 每行操作增加 **活动人员列表查看** → `router.push({ path: '/activity-registrations', query: { activityId: row.id } })`。
- **链接与二维码**：建议行内「报名链接」链接按钮 + `el-dialog` 展示完整 URL、`canvas`/`img` 二维码；URL = `` `${import.meta.env.VITE_WEB_ORIGIN ?? window.location.origin}/a/${id}` ``，与后端 `WEB_ORIGIN` 配置文档保持一致（可在 `GET activities/:id` 增加只读 `publicUrl` 字段，避免前后端不一致）。

二维码依赖：新增 npm 包（如 `qrcode` 生成 Data URL），仅后台页使用。

### 公开报名 `ActivitySignupForm.vue`

- Props：`activityId`；可选 `embedded` 样式（窄屏 padding、最大宽度）。
- 加载 `GET public/activities/:id`；`ENDED` 显示说明并禁用提交。
- 表单：俱乐部 `el-select`、名称、评分 `el-input-number` 或带 pattern 的 input、职业 select、提交前 `ElMessageBox.confirm`。
- 成功/失败 Message；**不提供**修改入口。
- 独立样式，避免依赖 AppShell；`meta viewport` 沿用 `index.html`。

### 活动查看 `ActivityRegistrations.vue`

- 进入时：`route.query.activityId` 优先；否则 `GET activity-registrations/activities` 取第一条为默认。
- 未选活动时列表空态提示「请选择活动」。
- 筛选：活动 select、俱乐部 select（随活动变化）。
- `el-table` 列：俱乐部、非凡者名称、评分、职业、出席状态（可 inline 改 select）、报名时间、操作（编辑/删除）。
- 排序：`sort-change` → 带 `sortBy/sortOrder` 重新请求（服务端排序，避免大数据前端 sort）。
- 导出：调用列表同条件 **不分页** 拉全量，走 `downloadRegistrationWorkbook`（新建，结构对齐 `export-members.ts`：标题行、摘要行、表头色、冻结行）。

## 关键流程

### 发布与传播

1. 管理员在 `/activities` 发布（逻辑不变）。
2. 列表或弹窗展示 `{WEB_ORIGIN}/a/{id}` 与二维码。
3. 玩家扫码/打开 → 公开页加载 → 提交 → 写入 `activity_registrations`，`attendanceStatus = NORMAL`。

### 活动查看维护

1. 管理员从签到列表跳转或侧栏进入，选中活动。
2. 列表加载；可改出席三态或 PATCH 整行；删除需确认。
3. 导出当前筛选下全部行。

### 结束活动

- `POST activities/:id/end` 不变。
- 公开 POST 拒绝；GET 仍返回 `status: ENDED`，前端禁用表单。

### members 清理（导入/删改）

| 移除项 | 说明 |
|---|---|
| `NEED_RENAME` / `renames` 对照流 | 不再因 `activity_attendances` 触发 |
| `claimAttendances` | 新建 member 不再认领 orphan |
| `syncAttendanceName` | 改名不再同步旧表 |
| 删除前 `activityAttendance.groupBy` | 删除人员按普通 delete，不保留 attendance  orphan |

导入确认：**本次名单没有的人直接删除**（或维持现网「未出现则删除」规则），不再分支「有历史参加则保留并对照改名」。与梳理版 UC-09 一致。

`members.activities()`：**不改查询源**，仍只读 `activity_attendances`；新报名不在活跃度弹窗出现。

## IP 限流与并发

- 计数方式：`COUNT(*)` WHERE `activityId` AND `submitIp`（成功记录）。
- 并发两次提交：依赖 DB 唯一约束 + 事务内先 count 再 insert；极端情况下两请求同时 count=4 可能都通过 → 最多 6 条，可接受或二次用 advisory lock；**实现优先简单 count+insert**，若需严格 5 可在 activity 行 `SELECT FOR UPDATE`（设计允许后续加强）。

重复名并发：唯一索引保证仅一条成功。

## 安全与风险

| 风险 | 对策 |
|---|---|
| 公开链接被刷 | IP 5 次/活动；可后续加验证码 |
| IP 伪造 | 信任反向代理头；内网部署需配置 trusted proxy |
| 活动查看全员可见报名 | 产品已定；含 `submitIp`，注意导出权限等同任意登录账号 |
| `WEB_ORIGIN` 与前端不一致 | 后端返回 `publicUrl` 或 env 文档统一 |
| 嵌入跨域 | 公开 API 需 CORS 与现网 `/apply` 一致；仅 GET/POST 公开路径 |

## 迁移与部署

1. Prisma migration：新增 `activity_registrations` 及枚举。
2. 部署顺序：先 migration，再 API，再 Web（旧前端仍调 attendance 会 404，需同版本发布）。
3. 不迁移 `activity_attendances` 数据到新表。
