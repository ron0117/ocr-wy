# 技术设计 · 签到表

依据 [需求梳理版](../detail/需求-签到表-梳理版.md) 的已确认口径，以及 Q1–Q5 的暂定结论。本版只定方案，不改代码。

## 目标与约束

管理员在现有俱乐部管理里发布活动，通过一个企业微信团队的内部应用发送可点击卡片。玩家在企业微信内绑定一个角色并签到。人员名单仍是 `members`，人员列表用绑定关系显示「是否绑定通知」。

沿用现有技术栈。提醒调度不引入 Redis 或 BullMQ。

| 已有能力 | 本需求中的用法 |
|---|---|
| Vue 3 + Element Plus + Vue Router | 后台活动页、人员列表新列、企业微信内活动页 |
| NestJS + JWT | 管理员接口继续用现有登录；玩家另发一种短期令牌 |
| PostgreSQL + Prisma | 活动、俱乐部关联、绑定、签到、发送记录 |
| 现有 `clubs` / `members` | 活动多选俱乐部；签到角色来自这些俱乐部的人员 |

约束：

- 全站只有一套企业微信内部应用，对应一个企业微信团队。俱乐部在创建时归入这个团队，不提供团队的创建和切换。
- 一场活动可以多选俱乐部，但所选俱乐部的团队必须相同。以当前只有一个团队为前提，跨团队选择在数据上直接拒绝。
- 一个企业微信成员只绑定一个角色，一个角色只绑定一个企业微信成员。绑定挂在 `members.id` 上，不挂在玩家名称上。
- 导入或编辑更新同一行人员时保留绑定。删除人员时同时删除绑定。
- 卡片和提醒由本系统调用企业微信「发送应用消息」。企业微信不保存活动，也不负责到点触发。
- 玩家页面必须从企业微信内置浏览器打开。个人微信和普通浏览器不能完成身份识别。

## 总体架构

```text
管理员浏览器                         企业微信内置浏览器
  活动签到 / 人员列表                   活动页
        │  JWT /api/v1                      │  玩家令牌 /api/v1
        ▼                                   ▼
NestJS
  clubs、members（扩展绑定列、删除时去掉绑定、解除绑定）
  activities（发布、结束、签到情况、再次发送）
  wecom（令牌、OAuth、可见范围、文本卡片）
  reminder（每分钟扫描到期提醒）
        │
        ▼
PostgreSQL
  wecom_teams, activities, activity_clubs,
  activity_recipients, wecom_bindings,
  activity_check_ins, activity_notifications
        │
        ▼
企业微信
  OAuth 识别成员
  应用可见范围
  message/send 文本卡片
```

管理员和玩家不共用登录。现有邮箱 JWT 的 `sub` 仍是 `users.id`。玩家令牌使用单独的类型标记，不能访问俱乐部和人员管理接口。

## 模块职责

| 模块 | 职责 |
|---|---|
| `wecom` | 读取企业配置、缓存 access_token、用 code 换成员 userid、读取应用可见范围、发送文本卡片 |
| `activities` | 发布、结束、签到情况、玩家打开活动、绑定、签到、再次发送 |
| `members` | 列表增加是否绑定；排序增加该列；删除人员时删除绑定；提供解除绑定 |
| `clubs` | 新建俱乐部写入当前企业微信团队。俱乐部已被活动使用时不允许删除 |
| `reminder` | 进程内定时任务。到提醒时间后给已绑定的本场人员发卡片，每场自动提醒只发一次 |
| Web 后台 | 俱乐部管理增加「活动签到」。人员列表增加一列 |
| Web 活动页 | 独立于后台壳，供企业微信打开 |

## 企业微信团队

环境变量提供这一套应用，启动时写入或更新唯一的 `wecom_teams` 行：

| 变量 | 含义 |
|---|---|
| `WECOM_CORP_ID` | 企业 ID |
| `WECOM_AGENT_ID` | 内部应用 AgentId |
| `WECOM_SECRET` | 应用 Secret |
| `WEB_ORIGIN` | 公网 HTTPS 源，用于卡片链接和 OAuth 回调 |

未配置这些变量时，俱乐部和人员功能保持可用。发布活动、拉取接收范围、玩家打开活动页返回「企业微信未配置」。

已有俱乐部在迁移时全部填上这个团队。之后新建俱乐部也写入同一团队。本版没有团队管理页面。

接收范围来自该应用的可见范围（部门、标签、成员），不读取全公司通讯录，也不把游戏人员名称当作接收人。部门若拿不到名称，选择器显示部门 ID，仍然可以按该 ID 发送。

## 关键流程

### 发布

1. 管理员提交标题、至少一个俱乐部、开始时间、接收范围，提醒时间可空。
2. 每个俱乐部必须属于当前用户，且 `wecomTeamId` 相同。否则拒绝。
3. 接收范围里部门、标签、成员至少有一项。
4. 提醒时间有值时，必须晚于本次发布时间。
5. 同一事务写入活动、俱乐部关联、接收范围，状态为已发布，并记下发布时间。
6. 事务提交后发送文本卡片。发送失败不回滚活动，只记下失败原因。已发布即可签到。
7. 卡片标题用活动标题。说明里写已选俱乐部名称和开始时间。链接指向该活动页。按钮文字为「去签到」。说明过长时截断俱乐部名称，保留链接。

发布后不能修改俱乐部、标题、开始时间、提醒时间和接收范围。需要停签时结束活动。

### 玩家身份

1. 卡片打开 `{WEB_ORIGIN}/a/{activityId}`。该路由不要求管理员登录。
2. 没有玩家令牌时，浏览器转到本系统的 OAuth 起点。起点 302 到企业微信授权地址，`scope` 为 `snsapi_base`，`state` 为带活动 ID 的签名值。
3. 企业微信带回 `code` 后，用 `code` 换 `userid`。成功则签发玩家令牌，再回到活动页。令牌只包含团队 ID 和 `userid`。
4. `state` 签名不对、`code` 无效，或不是企业微信内打开时，活动页说明无法识别身份，不展示角色，不允许绑定和签到。

### 绑定

玩家打开已发布的活动时：

- 尚无绑定：返回本场已选俱乐部里还没有绑定的角色，包含玩家名称和俱乐部名称。确认时写入绑定。角色已被占用，或该成员已经绑过别人，返回冲突，不覆盖原绑定。
- 已绑定且角色属于本场任一俱乐部：返回该角色，并带上是否已签到。
- 已绑定但角色不属于本场俱乐部：返回已绑定的角色名称和俱乐部，不允许改选，不允许签到。

绑定只在活动处于已发布时允许。结束后不能新绑定。

### 签到

已发布、已绑定、且角色属于本场已选俱乐部时，写入一条签到。同一活动、同一角色只有一行。再次请求不新增，返回原来的签到时间。

未发布、已结束、未绑定、角色不在本场俱乐部，都不写入。

### 提醒

每分钟检查：已发布、填写了提醒时间、提醒时间已到、尚未成功发送过自动提醒。

用条件更新先占住这场活动的提醒名额，再计算接收人：已绑定，且角色属于本场已选俱乐部的企业微信 userid。没有这样的人时记为已发送、接收人数为 0，避免下一分钟重复扫描。

发送对象是这些 userid，不是发布时选择的部门或标签。未绑定的人不会收到提醒。

自动提醒失败时保留失败记录，本分钟不再重试。管理员可以再次发送。

### 解除绑定和删除人员

解除绑定只删绑定行，不删人员，不删历史签到。该企业微信成员之后可以再绑一个未被占用的角色。

删除人员时，在同一事务里删除该行的绑定，再删除人员。该成员因此不再占用这个企业微信身份。签到记录随人员删除，因为签到情况以当前人员为准，不保留已删人员的名册。

编辑人员、以及按「俱乐部 + 玩家名称」覆盖导入时，不改绑定。

俱乐部已被任一活动选中时，删除俱乐部返回冲突。先结束或保留活动，避免活动失去已选俱乐部。

## 接口

前缀 `/api/v1`。管理员接口使用现有 JWT。不属于当前用户的俱乐部、人员、活动返回 404。

### 管理员

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/wecom/audience` | 当前应用可见的部门、标签、成员，供发布时选择 |
| POST | `/activities` | 发布。见下方请求 |
| GET | `/activities` | 当前用户的活动列表 |
| GET | `/activities/:id` | 活动详情 |
| POST | `/activities/:id/end` | 结束。已结束再次调用仍返回已结束 |
| GET | `/activities/:id/check-ins` | 本场已选俱乐部的当前人员及签到情况 |
| POST | `/activities/:id/notifications` | 再次发送。正文 `{ "kind": "publish" \| "remind" }`，仅已发布可发 |
| DELETE | `/members/:id/wecom-binding` | 解除绑定。未绑定时返回已是未绑定 |

`POST /activities` 正文：

| 字段 | 规则 |
|---|---|
| title | 必填，去空格后非空 |
| clubIds | uuid 数组，至少一项，去重后校验归属和团队 |
| startsAt | ISO 时间 |
| remindAt | 可空。有值则必须晚于服务器当前时间 |
| partyIds / tagIds / userIds | 字符串数组，三者合计至少一项 |

发布成功返回活动 id、状态、以及这次发布通知是否送出。

`GET /members` 每行增加 `notifyBound`（布尔）。`sort` 增加 `notifyBound`。升序时未绑定在前。新增和编辑的请求体不含该字段；传入则按现有白名单拒绝。

`GET /activities/:id/check-ins` 每一行：

| 字段 | 含义 |
|---|---|
| playerName / clubName | 人员及其俱乐部 |
| notifyBound | 是否已绑定 |
| checkedIn | 是否已签到 |
| checkedAt | 未签到为空 |

只含本场俱乐部的当前人员。未选俱乐部的人员不出现。

错误：

| 情况 | 结果 |
|---|---|
| 未选俱乐部、接收范围为空、提醒时间不晚于现在、标题为空 | 400 |
| 俱乐部或活动不存在，或不属于当前用户 | 404 |
| 所选俱乐部团队不一致 | 400 |
| 俱乐部仍被活动引用时删除 | 409 |
| 企业微信未配置，或发布时企业微信拒绝发送 | 活动仍为已发布；通知记录为失败。配置缺失导致无法发布时，不创建活动 |
| 对已结束活动再次发送 | 409 |

### 玩家

这些接口不使用管理员 JWT。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/wecom/oauth/start` | 查询参数 `activityId`。302 到企业微信 |
| GET | `/wecom/oauth/callback` | 校验 `code` 和 `state`，签发玩家令牌后 302 回活动页 |
| GET | `/player/activities/:id` | 活动摘要、绑定状态、可选角色或签到状态 |
| POST | `/player/activities/:id/binding` | `{ memberId }` |
| POST | `/player/activities/:id/check-in` | 无正文。重复签到返回原 `checkedAt` |

`GET /player/activities/:id` 的 `phase`：

| phase | 含义 |
|---|---|
| `unbound` | 附带 `candidates`：未被占用的角色 |
| `ready` | 已绑定且属于本场，附带角色和 `checkedAt` |
| `other_club` | 已绑定其他俱乐部的角色，不能签到 |
| `closed` | 活动已结束。已有签到仍返回 `checkedAt` |

绑定冲突返回 409。已结束时绑定和签到返回 409。

## 前端

后台仍走 `AppShell`。企业微信活动页不套后台侧栏，也不读取 `ocr_token`。

| 菜单或入口 | 路由 | 界面 |
|---|---|---|
| 活动签到 | `/activities` | 列表：标题、俱乐部名称、开始时间、状态。新建用对话框：多选俱乐部、标题、开始时间、提醒时间、接收范围。行内可结束、查看签到、再次发送 |
| 活动签到情况 | `/activities/:id` | `el-table`：玩家名称、所属俱乐部、是否绑定通知、是否已签到、签到时间 |
| 人员列表 | `/members` | 在「入会时间」和「操作」之间增加「是否绑定通知」，文案为已绑定或未绑定，表头可排序。已绑定行增加「解除绑定」 |
| 企业微信活动页 | `/a/:id` | 窄屏。未绑定则选角色；已绑定且属于本场则显示签到；已签到显示时间；其他俱乐部显示说明 |

`/a/:id` 标为公开路由，避免被管理员登录拦截。玩家令牌放在 `sessionStorage`，键与 `ocr_token` 分开。

接收范围用三组多选：部门、标签、成员。数据来自 `GET /wecom/audience`。未配置企业微信时，新建按钮说明原因，不提交发布。

## 技术选型与备选

| 决定 | 原因 | 不采用 |
|---|---|---|
| 文本卡片 `textcard` | 有标题、说明和整卡跳转，足够打开活动页 | 模板卡片。按钮交互更重，本需求没有卡片内直接签到 |
| 应用可见范围作为接收人来源 | 发得出去的人就是可见范围内的部门、标签和成员 | 同步全公司通讯录。需求不把通讯录当人员名单，也多要一套通讯录权限 |
| 玩家使用另一种 JWT | 现有策略会按 `users.id` 查管理员，不能把企业微信 userid 塞进同一登录 | 给每个企业微信成员建邮箱账号 |
| 绑定表独立于 `members` | 人员列只需要是否存在绑定；解绑不改排名和评分 | 在 `members` 上加可空 `wecomUserId`。能做，但团队和绑定时间挤在人员行上，解绑还要清空业务列以外的身份字段。独立表更符合「绑定是通知关系」 |
| `@nestjs/schedule` 每分钟扫描 | 当前没有 Redis。提醒量是活动场次，不是人员消息队列 | BullMQ。梳理未要求横向扩展，引入后还要补队列基础设施 |
| 自动提醒用 `remindClaimedAt` 占位 | 多开一个 API 进程时不会发两次 | 只靠内存锁。进程一多就失效 |
| 签到情况按当前人员左连签到 | 未绑定、未签到的人也要出现在表里 | 只查签到表。未签的人会消失 |

## 风险与对策

| 风险 | 对策 |
|---|---|
| 本地 `localhost` 不能被企业微信当作可信域名 | 设计依赖 `WEB_ORIGIN` 为已备案的 HTTPS 域名。未配置时发布接口直接失败，不写半成品活动 |
| 接收人不在应用可见范围内 | 选择器只列可见范围。企业微信仍可能拒收部分成员，失败写入通知记录，活动保持已发布 |
| 两名玩家同时选中同一角色 | 数据库唯一约束，后到的请求 409，前端重新拉取可选角色 |
| 企业微信已收下消息，但本系统超时未记成功 | 自动提醒不立刻重试。管理员看到失败后再手动发送，避免定时任务连发 |
| 卡片说明写不下很多俱乐部名称 | 超出企业微信文本卡片说明长度时截断，活动页展示完整俱乐部名单 |
| 删除人员会带走该角色的签到记录 | 与「签到表只看当前人员」一致。解除绑定不删签到，删除人员才删 |
| access_token 过期 | 按企业微信返回的有效期提前刷新，发送前使用缓存的令牌 |

| UC-01、验收 1、7 | `POST /activities`；`activity_clubs`；状态 `PUBLISHED` 后即可签到；`startsAt` 不参与签到判断 |
| UC-02、验收 2 | `activity_recipients` 与文本卡片；链接为 `/a/:id` |
| UC-03、验收 9 | `remindAt` 可空；定时任务只把卡片发给已绑定且属于本场俱乐部的 userid |
| UC-04、验收 3、4 | `wecom_bindings` 双唯一；候选角色排除已占用行 |
| UC-05、验收 5、6 | `activity_check_ins` 联合主键；`other_club` 不允许签到和改绑 |
| UC-06、验收 8 | `notifyBound` 与 `sort=notifyBound`；写人员接口不接收该字段 |
| UC-07 | `GET /activities/:id/check-ins` 左连当前人员 |
| UC-08、Q3 | `DELETE /members/:id/wecom-binding` |
| UC-09 | `activity_notifications`；`POST /activities/:id/notifications` |
| Q1 | `remindAt` 为空不创建自动提醒 |
| Q2 | `POST /activities/:id/end`；结束后绑定和签到返回 409，已有 `checkedAt` 仍可读 |
| Q4 | 删除人员级联删除绑定 |
| Q5 | 路由 `/activities/:id`，不另做跨活动的人员签到总表 |
| 一团队 | 唯一 `wecom_teams`；俱乐部带 `wecomTeamId`；发布时校验一致 |
